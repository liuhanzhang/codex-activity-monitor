# 实施计划

日期：2026-10-22。状态：P0–P4 已执行，完成定向验证并更新日常 collector，实际证据及边界见[实施结果](implementation-results.md)。本文件保留实施要求；[独立可行性原型](feasibility-results.md)不作为产品验收。行为以[修复说明](README.md)的 R01–R12 为准，验证要求见[验收计划](validation-plan.md)。

## 1. 最小实现方式

沿用 `history.py` 读取 Codex JSONL，沿用 `Engine` 处理实时活动。在现有结构内增加后台历史刷新和可重复执行的历史合并入口：

```text
已接入会话的 JSONL 增量索引 ─┐
                            ├→ 历史基础 + 实时补充 → 快照 / 总速度 / 时间线
当前实时协议与流式增量 ──────┘
```

JSONL 已保存的轮次、活动状态和内容引用构成基础；实时信息补齐尚未落盘的活动和缺失字段。实现可以使用现有结构的增量更新，不要求每次刷新重建整个状态，也不要求把全部历史活动放进 `Engine`。

不新增第二份正文存储，不迁移为通用事件框架。优先扩展现有模块；只有后台调度确实需要隔离时才拆出小型 helper。

## 3. 后台读取范围与节奏

后台校正只处理现有接入范围：正在工作的主／子线程、仍有未决活动的线程，以及有实时完成信息等待落盘的最近线程。保持现有按需历史入口，不在本轮扫描并展示所有旧聊天。

建议以现有约 1 秒快照节奏安排候选刷新；有界队列按不同线程去重，同一线程不能因多条 child relation 重复排队。缺失文件沿用退避；一次失败不能阻塞其他线程。源记录可读、候选不被积压且身份匹配时，以两个成功后台刷新周期内完成校正作为定向验收目标，不承诺任意大小历史的首次索引时限。

复用已定位路径和 offset。只有查找新线程或原路径失效时才做有界路径发现，不按每个 collector tick 扫描整个 Codex Home。最近完成项沿用现有保留范围；等待落盘任务的连续高频重试必须有界，超过后降为按需或退避刷新，不能永久占用活跃扫描队列。

后台返回带来源身份和索引版本的必要元数据副本，由现有状态更新路径应用。查询与后台读取复用索引能力，但不能为方便共享而在持有事件锁时获取可能执行完整文件读取的历史锁。具体缓存所有权以简单、可验证的方式确定，避免为同一线程建立两套周期性全量读取。

## 4. 合并所需信息与规则

### 4.1 身份和阶段

复用现有 `scope_id / thread_id / turn_id / namespace / item_id`，不重造活动 ID。scope 必须对应已验证的数据源，不能因为 bridge 进程重连就丢失同一活动的身份；不同 scope 不合并。

canonical 命令执行、模型参数生成、原始调用及调用返回维持既有区分。只使用已验证的 canonical ID 或协议显式关联；外层 `exec` 的返回可能包含后台进程句柄，不能代替内部命令完成。仅包含原始完整参数的历史记录，不能使其关联工具被判定为已执行或完成。

### 4.2 完成状态

对 JSONL 中身份匹配、语义明确的终止记录：

1. 保存源状态、可用退出码、起止时间及记录引用，解除对应实时运行中覆盖。
2. 从当前活动／当前生成贡献中移除已经确认完成的项；保留历史阶段和已有统计样本。
3. 重复应用不得增加活动数量、重复累计官方用量或改变完成时间。
4. 较早的历史开始记录、迟到或重放的实时开始事件不能撤销已经确认的结束；新的 turn／item 按新身份正常工作。

实时先收到终止事件时，不等待 JSONL 才结束活动。历史后续到达补齐可用字段；空字段不覆盖已有有效字段。明确的来源冲突单独保留，不用“最后到达者胜出”解决。

### 4.3 时间与保留窗口

`Engine` 当前大量使用单调时钟，JSONL 的 `started_at_ms / completed_at_ms` 是墙上时间。不能直接把历史毫秒值写进单调时钟字段，也不能用“今天读到记录”的时间伪装成执行结束时间。

展示起止边界优先复用已有来源时间表示。必要时增加最少的可选源时间字段；内部活动停止条件、展示耗时和保留期限分别使用正确的时间基准。源报告的执行耗时与起止时间差保留各自含义，不能为了数值相同重写来源。

历史更新不能把已结束很久的会话重新延长为“最近完成”，也不能把已终止流显示成刚刚高速生成。没有可靠起止字段时保持未知，不从轮次结束、文件修改时间或相邻记录补造。

### 4.4 缺口和生成速度

观测缺口描述历史覆盖，不是永久活跃标记。JSONL 确认活动结束后，保留缺口说明，停止该活动影响当前总速度；其他未关联事件、未知流、身份冲突仍继续生效。

gap 后尚无终止证据的活动保留未决身份并显示未知，不假设成功完成，不再持续显示已知运行时长。需要区分“未知是否还在工作”与“已可靠确认没有工作”，不能用清空 active 集合把未知总速度变成零。

生成速度保持现有实时分词、独立流去重及完整覆盖要求。历史补入不重放为实时 delta，不加入当前速度窗口，不清除跨缺口的速度质量，不修改官方用量归属。

## 5. 实施阶段与退出条件

| 阶段 | 工作 | 退出条件 |
| --- | --- | --- |
| P0 | 固定问题来源和基线；提取最小脱敏 fixture，复现历史 completed、实时仍 active 的分歧 | 原始来源身份核对通过；复现与采集丢失原因的假设分开记录 |
| P1 | 暴露必要历史元数据，完成历史基础与实时补充的合并 | 同一活动正确结束；重复、迟到、跨轮、参数／执行混淆的反例通过 |
| P2 | 接入有界后台读取，更新快照、汇总与时间线 | 面板关闭也能校正；慢读不阻塞采集；同线程重复引用不增加重复索引任务 |
| P3 | 验证时间、缺口、重启和原始详情兼容 | 不混用时钟，不制造新速度、不延长旧会话保留窗口；原始内容来源保持 |
| P4 | 对照问题来源并执行有限日常验收，记录实际加载版本 | 已观察到的变化和其他仍不可用原因分别记录；新增实施结果说明通过项和限制 |

先用脱敏来源副本和隔离 collector 验证，不通过向日常 `events.sock` 注入伪造完成事件修正界面。日常重载若有必要，应记录观测边界，不能将重启后旧状态消失当作历史合并已经成功。
