# 修复前可行性实验

日期：2026-10-22。状态：本文保留修复前隔离原型的 9 个场景结果，正式实现和验收见[实施结果](implementation-results.md)。实验源码基线：`5579bd527a0f`。

## 1. 结论

“以 JSONL 为基础，补充实时观测”的方案可以在现有模块上实现。原型已经打通：后台读取追加的 JSONL 完成记录，按同一命令身份结束现有 `Engine` 中的残留活动，再输出更新后的快照和汇总；整个纠正过程没有调用时间线查询。

没有发现需要用户补充决定的阻塞项。这个结论支持开始正式实现，不代表日常 Monitor 已修复，也不代表本章全部验收场景已经通过。

## 2. 实验方法与来源

可复用脚本：[`jsonl_reconciliation_probe.py`](../../experiments/timeline/jsonl_reconciliation_probe.py)。使用现有 `HistoryProvider / RolloutIndex`、`Engine`、`TimelineBook`、`TimelineQuery`，在实验脚本内增加一个小型后台读线程和历史合并适配器。

- 所有实时开始、心跳、命令和完成事件都是合成 fixture，命令本身没有被执行，也没有发起模型请求。
- fixture JSONL 与结果写入独立、Git 忽略的 `.local/diagnostics/jsonl-feasibility-20261022/`。
- 后台线程独占历史索引，只把分离的必要元数据交给原型主循环；读取结果没有伪装成新收到的实时协议事件。
- 原型直接更新实验 `Engine` 的活动状态和退出码，并在快照投影中补充源起止时间。墙上时间不写入现有单调时钟字段。
- 可校正场景均在时间线查询次数为 0 时完成状态纠正；其后才对适用场景发起查询，核对同一命令显示已完成。
- 日常 `events.sock / tl.sock`、观察租约、接入配置、collector、GUI 与产品源码没有被修改或重启。

同时只读复查了前次真实问题的原始 canonical 完成记录：记录哈希与前次证据一致，命令 ID 相同，状态仍为 `completed`，退出码为 0。没有重新复制或完整重放真实会话，前次已证明的来源解析能力不重复做大范围验证。

## 3. 九个定向场景

| 场景 | 实际观察 |
| --- | --- |
| 延迟追加完成记录 | 没有时间线查询，后台自行使命令退出活跃集合；缺口保留，隔离场景总速度恢复为已知零 |
| JSONL 只有半行末尾 | 半行不产生完成事实；补齐剩余内容和换行后正常校正 |
| 只有 raw 参数与外层调用返回 | 即使 `call_id` 对上命令 ID，也不替代 canonical 命令完成；命令保持未决，总速度仍未知 |
| 不同 item 或 turn 的完成记录 | 不校正原命令，不按文本、名称或时间近似关联 |
| 同线程新回合已经生成 | 旧命令结束后活动数从 2 变为 1；新回合与独立生成流保留，旧阶段的历史缺口仍存在 |
| 实时先完成，历史稍后落盘 | 实时完成立即生效；历史追加后补齐信息，不重新打开活动 |
| 128 个重复候选引用 | 后台候选去重为 1 个线程，不按引用数重复读取 |
| 读线程人为延迟 250 毫秒 | 原型主循环仍可处理心跳与快照；最终完成历史校正 |
| 十小时前已完成的记录 | 使用源时间固定耗时，不更新线程最近活动时间；原残留命令结束后，线程按已有过期逻辑退出 |

读取重复批次后，活动数量保持稳定。普通结束场景的当前线程缺口仍保留；新回合场景沿用现有新轮基线，当前轮没有旧缺口，旧命令的历史阶段继续保留缺口。这两个范围没有混为同一个质量标记。

源起止时间差在 fixture 中为 0.353 秒，命令源报告的执行耗时约 0.350 秒。原型验证前者作为来源区间，不要求它们相等，也不修改源记录。

修复前最终结果保存在 `.local/diagnostics/jsonl-feasibility-20261022/run-02/result.json`，9/9 通过。`run-01` 是首次通过结果；之后补充了新轮合并前的活动数及历史缺口范围记录，再以当时的最终脚本运行 `run-02`。

`run-02` 对应的修复前脚本 SHA-256：`2bab6ae155f7023e7aa137dfa4075237871a24dea68b0e8db9d82f7861be48a6`。私有结果同时保存了被使用产品模块的哈希。

正式修复后，脚本断言已兼容“gap 后未决、不能继续宣称已知运行”的行为；当前代码复跑保存在 `run-03/result.json`，同样 9/9 通过，当前脚本哈希见该结果。它仅保证这个历史实验入口仍可使用，不替代正式 collector 和产品验收。

原型后台刷新间隔为 25 毫秒；这是为了缩短实验等待，不是产品默认值或日常时限承诺。人为慢读场景中，原型主循环执行 53 次，最大采样间隔约 12.07 毫秒，校正等待约 232.62 毫秒。它证明本次原型把等待留在读线程，不能作为真实 collector、磁盘慢读或大历史的性能基准。

## 5. 对正式实现的具体影响

1. 复用现有 JSONL 解析器可行。canonical 完成状态和时间可以直接取得；退出码需要从对应原始完成记录提取少量元数据，当前 phase 摘要没有这个字段。
2. 后台读取应与实时事件处理分开，只交付必要元数据副本，避免把完整历史读取放进事件锁或 GUI 查询路径。
3. 结束状态可以解除活跃贡献而保留 gap。源时间需在合并后的快照中正确表达，不能把“读到历史的时刻”当作执行结束，也不能混用墙上时间和单调时钟。
4. 原型没有增加新的状态框架或内容数据库，正式实现仍按[原实施计划](implementation-plan.md)在现有模块中补齐合并路径。

## 6. 未覆盖的部分

原型适配器只处理本次实验需要的 canonical 命令和轮次完成摘要，不是可直接部署的通用修复。它没有替换正式 collector，也没有验证 Swift DTO、原生界面、实际后台调度锁、历史文件首次大规模索引、不同 Codex 版本或长时间运行。

gap 后未知活动的完整展示、两来源终止冲突、文件替换／截断、跨观察重启、官方用量去重及其他未知流对总速度的影响，仍按[验收计划](validation-plan.md)在正式实现时做相应定向验证。当前通过的 9 个原型场景不能替代整张验收矩阵。
