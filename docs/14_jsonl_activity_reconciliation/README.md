# 以 JSONL 为基础的活动状态修复

日期：2026-10-22。状态：修复已实现，完成 232 项相关测试、隔离 collector、原始来源及有限日常验证，日常 collector 已载入。实际证据和边界见[实施结果](implementation-results.md)。实现前源码基线：`5579bd527a0f`。

## 1. 已确认的方向

```text
展示内容 = Codex JSONL 中已保存的记录 + 当前实时观测的补充
```

已落盘的消息、参数、工具结果和完成状态以 Codex 自己的 session JSONL 为基础；尚未落盘的活动、历史没有保留的阶段信息和实时生成速度由现有实时观察链路补充。同一活动的明确历史完成记录出现后，实时侧残留的“运行中”状态不再生效。

本轮复用现有历史索引、实时引擎、时间线和快照，补齐它们之间的合并与后台刷新。无需另建通用状态框架、独立聊天数据库或第二套完整内容存储。

## 2. 问题与已取得的证据

2026-10-21 排查发现：一个子智能体的回合已完成，Monitor 仍把其中一条 `rg` 命令显示为运行中超过 10 小时。该残留活动带有 `observation_gap`，继续参与当前活动判定，使全局总速度不可用。

按完整 `scope / thread / turn / item` 身份核对，Codex JSONL 和 Monitor 记录指向同一条命令，并非按命令文本或相邻时间猜测：

| 来源 | 已观察到的事实 |
| --- | --- |
| Codex JSONL 的 canonical `event_msg / item_completed` | `status=completed`、`exit_code=0`；完成时间为北京时间 2026-10-21 00:39:36.247；源执行耗时约 0.350 秒 |
| 修复前实时快照 | 回合 `completed`，命令仍为 `inProgress / active=true / turn_bound=false`，耗时持续增长 |
| Monitor 观测时间线元数据 | 相同命令缺少结束时间，状态为 `unknown`，带有 `observation_gap` |
| 现有 `RolloutIndex` 历史解析器 | 能读出相同命令的 `completed` 和历史起止时间 |
| 隔离内存复现 | 漏掉命令完成事件、再接收回合完成，命令仍活跃；补入同一 ID 的完成信息后，活动结束，保留观测缺口也不再阻止该活动退出汇总 |

隔离复现没有修改日常 collector。它证明结束信息可以解除残留状态，不等同于正式实现或自然运行验收。复现中没有其他不可靠活动，因此总速度恢复为已知零；真实运行中若还有未关联事件或其他不完整流，修正这一条命令并不保证全局总速度立即可用。

命令的实际输出约 272 万字符，其结束后约 84 毫秒，观测侧记录了缺口；同一 bridge 的累计健康信息也存在队列溢出和解析错误。这些现象支持采集压力的可能性，但没有保留当时逐帧输入，不能断言具体哪条完成帧如何丢失。修复不以确定最初丢失原因作为前提。

完整来源路径、身份、记录行号和本机诊断保存在 Git 忽略的 `.local/diagnostics/stale-command-20261021/evidence.json`。文档仅保留必要的状态、时间和验证结论，不提交原始会话、命令输出、快照或数据库。

## 3. 当前实现为什么没有自行纠正

当前主要有两条数据路径：

```text
Codex 实时协议 / 流式增量 → Engine → snapshot → 当前活动和总速度
Codex session JSONL → HistoryProvider → TimelineQuery → 时间线和详情
```

`TimelineQuery.bundle()` 读取并合并历史，但结果仅供该次查询使用，没有纠正实时引擎。`Engine` 为允许进程跨回合运行，在回合完成时保留已确认进程身份的命令；活动还在活跃集合中，又阻止线程过期。缺失命令自身的结束事件后，这条记录就一直残留。

JSONL 已有结束事实而快照仍显示运行中，说明当前合并缺少一条有效路径。本轮需要让历史基础同时影响当前活动、总速度和时间线，并且不依赖用户打开面板。

## 4. 修复规则

| 编号 | 规则 |
| --- | --- |
| R01 | 已保存的记录以身份校验通过的 Codex JSONL 为基础；实时观测补充尚未保存的活动、字段及速度。所有展示执行同一套合并规则。 |
| R02 | 只有完整作用域和明确 ID 匹配时才合并。同一文本、命令名称、路径、相邻时间或同名子智能体不能建立身份。保留现有 canonical、参数生成等阶段的区分。 |
| R03 | 同一 canonical 活动的历史完成记录能结束实时残留活动，采用源状态、退出码和可用的源时间。重复读取不重复创建活动；迟到开始事件不能重新打开已完成活动。 |
| R04 | 实时已完成而 JSONL 尚未追加时，立即展示实时完成状态，保留必要补充；不等待落盘才结束，也不能被较早的历史开始记录回退为运行中。 |
| R05 | JSONL 中仅出现完整工具参数，或外层 `exec` 返回结果，不等于其中每个命令都已结束。后台进程仍等待自己的 canonical 完成记录或其他已验证、明确关联的终止证据。 |
| R06 | 回合状态与工具状态分别合并。回合完成不强制结束有可靠证据仍在运行的后台命令；旧回合的完成记录也不能结束同线程的新回合。 |
| R07 | 观测中断后，缺少结束证据的活动显示状态未知；不把持续时间增长解释为命令仍在运行，也不根据静默、超时或文件暂未追加判定成功完成。 |
| R08 | 历史完成状态与当时的观测缺口可以并存。完成活动退出当前活跃集合后，其旧缺口不再阻止当前总速度；其他不可靠活动仍按原规则使总速度显示 `—`。 |
| R09 | 实时 token/s 继续由独立、去重后的实时流计算。历史正文、读取文件速度、历史完成时间和最终用量不能补造漏采区间的生成速度。 |
| R10 | 历史校正由后台主动执行，覆盖现有已接入的活跃、存在未决活动及等待落盘的最近完成会话；面板关闭时同样有效。 |
| R11 | JSONL 暂缺、读失败、部分末行、身份冲突或不支持的记录保留明确不可用状态。未找到完成记录不是“仍在运行”或“已经完成”的充分证据。 |
| R12 | 历史校正不制造新的活动时间。旧命令今天才被读到完成记录，也不能因此重新进入“最近完成”的十分钟窗口。 |

这里的“历史优先”针对同一活动的有效历史事实，不是用空值覆盖实时字段。若两个来源给出互相矛盾的终止信息，保留冲突及来源，不按到达顺序静默覆盖。

## 5. 预期结果

这次 `rg` 在下一次成功历史校正后应满足：

1. 原命令显示已完成，退出码为 0，时间来自源记录，不再增长。
2. 原命令不再计入当前活跃活动；所属回合和子智能体依现有归组、保留规则处理。
3. 历史里的观测缺口与不可恢复速度继续如实保留。
4. 菜单栏、聊天列表、所选轮次时间线和详情对这条命令的完成事实一致。
5. 新回合与其他会话的活动、速度和不完整覆盖判定不被一并清除。
