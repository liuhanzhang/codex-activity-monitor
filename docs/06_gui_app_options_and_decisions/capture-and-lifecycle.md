# 采集路线、接入周期与卸载恢复

日期：2026-10-16 更新。状态：决策整理。**继续使用现有包装器；首次启动配置、App 内恢复后手动删除，不增加常驻卸载 Helper；App 缺失时通过启动脚本回退原版 CLI。** 此前的候选调查保留，不作为首版替代路线；回退机制已实现并通过隔离进程验证；本机迁移与剩余验收见 [实施结果](implementation-results.md)。

总览见 [README](README.md)，已确认交互与当前本机范围见 [产品需求](requirements.md)，执行步骤见 [实施计划](implementation-plan.md)，语言和发行方式见 [技术栈与打包](technology-and-packaging.md)。

## 1. 现有包装器承担哪些职责

当前包装器不在 Desktop 渲染进程中注入代码。它位于 Desktop 主进程与原版 CLI 的 `app-server` 之间：

| 职责 | 当前做法 | 提供的信息 |
| --- | --- | --- |
| 承载原业务通信 | 启动原 CLI，转发 stdin / stdout，传递信号与退出状态 | 维持原连接；包装器故障可能影响 Codex。 |
| 观察完整协议 | 复制并过滤请求、通知和生命周期事件 | Thread / turn / item 关联、工具活动、审批内部状态、完成与失败等。 |
| 取得生成增量 | 为子进程开启指定 TRACE，直接读取 stderr | 正文、工具参数、可见摘要等模型接收增量。 |
| 隔离观察负载 | 有界队列、过滤后 IPC、独立采集器 | 采集器或显示故障可降级为观测缺口，不阻塞正常转发。 |

“速度来自日志”不表示当前已经在尾读某个原生日志文件。现有产品读取的是包装器截获的 stderr 管道，同时使用协议补充身份、生命周期和可信度。

源码依据：[bridge.py](../../src/codex_progress_monitor/bridge.py)、[events.py](../../src/codex_progress_monitor/events.py)、[engine.py](../../src/codex_progress_monitor/engine.py)和[既有架构](../02_product_mvp/architecture.md)。

## 2. 三条采集路线的比较与选择

| 路线 | 实现思路 | 优点 | 代价 / 未确认事项 | 本轮选择 |
| --- | --- | --- | --- | --- |
| 一：原生日志 + hooks | 原版 CLI 正常连接 Desktop；Monitor 尾读 Desktop 日志，并接收 hooks | 不替换 CLI 启动入口，观察程序退出不直接切断 stdio | 仍需日志开关与 hook 配置；生成内容先落盘；分块、轮转、丢行、延迟和多后端归属未验证 | 不采用；保留静态调查记录。 |
| 二：仅 stderr 接入器 + hooks | 使用轻量启动器取得 stderr，stdin / stdout 直接继承，不再复制业务协议 | 可缩小包装器职责，减少业务通信转发逻辑 | 仍需改变启动入口，仍有接入与恢复工作；hooks 无法覆盖所有现有状态 | 不采用。 |
| 三：现有完整包装器 + TRACE | 保留协议观察、stderr 增量和现有采集核心 | 已有实现与有限运行验证，覆盖现有状态和用量语义 | 包装器位于关键通信路径，仍需维护转发、日志、信号与生命周期 | 已选择。 |

选择三的理由是复用已有能力与证据，避免为 GUI 同时引入新的采集与状态语义。该选择不等于证明其他路线不可行，也不代表已经完成长期、全场景可靠性验证。

## 3. hooks 可以提供什么

本轮核对了官方文档、本地公开源码的 schema，以及本机安装 CLI 的 hooks 开关。它们支持下表的能力判断；没有注册新的 hooks，也没有验证它们在 Desktop 中的实际回调覆盖率。

| 信息 | 可用 hook / 字段 | 边界 |
| --- | --- | --- |
| 聊天与环境 | `session_id`、`cwd`、`model` | 没有直接的聊天显示名称字段；子代理事件的 session / agent 身份需按其 schema 解释。 |
| 提交与回合 | `UserPromptSubmit`、`turn_id` | 不能把每次回调等同于一个独立、已完整观测的回合。 |
| 本地工具前后 | `PreToolUse`、`PostToolUse`、`tool_use_id`、输入与输出 | 参数已完整；不是参数生成过程。前置 hook 也不证明实际执行已开始。 |
| 审批请求 | `PermissionRequest` | 不等价于完整的审批 / 用户输入解决状态，不用于重复提供审批界面。 |
| 压缩与子代理 | `PreCompact` / `PostCompact`、`SubagentStart` / `SubagentStop` | 可补充阶段和身份，不提供逐段 token 增量。 |
| 停止与中断 | `Stop`、`Interrupt` | Stop 可被后续逻辑继续；中断、失败、崩溃和最终完成不能直接合并为一种状态。 |
| 实时 token 增量与官方用量 | 没有相应连续回调 / 通用 usage 字段 | 仍需其他数据源，不能用最后一条回答或 hook 次数估算实时速度。 |

托管工具如 `WebSearch` 不经过这些本地工具 hooks，部分专用路径也可能绕过。同步 hook 会被 Codex 等待，异步 hook 则可能排队、乱序或在会话结束时取消；非托管定义需要用户信任。若以后使用，回调应快速返回、保持观察用途、不注入上下文或审批决定。

hooks 自身也需要配置和卸载管理。官方说明还指出，`transcript_path` 指向的会话格式不是稳定的 hook 接口。

依据：[官方 Hooks](https://learn.chatgpt.com/docs/hooks)。保留现有方案不需要为 GUI 额外安装这些观察 hooks。

## 4. 原生日志路线的可行性调查

### 4.1 找到的静态路径

2026-10-15 对安装版 Desktop `26.1007.71326` / build `20398` 的定向检查发现，本机 stdio 路径存在以下链路：

```text
Desktop 将 RUST_LOG 传入原 CLI，并使用 JSON 日志格式
    → CLI 输出 stderr TRACE
    → Desktop 将 stderr 数据块作为 Codex CLI stderr 的 debug 日志
    → Desktop 原生日志文件
    → Monitor 尾读、重组、解析与关联
```

`CODEX_MAX_LOG_LEVEL=debug` 可在该安装版中使 Desktop 保留 debug 日志；prod 默认级别为 info。`RUST_LOG` 控制后端所需 TRACE。前者是安装版内部实现，不是本项目可以假定长期稳定的公共接口。

这条路线可以避免将 `CODEX_CLI_PATH` 指向 Monitor，但不能据此承诺免配置。上述开关作用于新启动的进程；daemon、远程和其他传输路径没有按同等方式验证。

精简来源、模块 SHA-256、定位点和未验证范围见 [静态调查记录](native-log-static-observations.json)。REA 全模块语义分析未完成；链路中的后续部分通过当前安装包的定向源码读取确认。没有把静态代码当作运行实测。

### 4.2 延迟、完整性与内容落盘

- 文件尾读不必等待数据真正写入 SSD。操作系统文件缓存中的数据对读者可见后即可读取；文件缓冲不意味着无法达到每秒刷新的体验。
- 路线一额外经过 Desktop 处理、写入与文件监听，可能增加延迟和抖动；须使用原始事件时间戳计算速度，不能把文件增长速度或批量到达时间当作生成速度。
- 当前安装版以 stderr 数据块记录并执行 `trim()`，存在跨块重组与多后端交错的问题，不能假设每条外层记录包含一条完整 Rust JSON。
- 原生日志有轮转、背压和丢行路径；需要独立验证能否完整取得长工具参数及所有目标生成流。
- 完整生成内容会先写入 Codex 原生日志，改变当前由包装器过滤、默认不额外保存全文 TRACE 的边界。
- Monitor 退出后，已运行的后端仍持有 TRACE 环境，原生日志可能继续增长，直到该后端结束或重新启动。

另外，本地公开源码中的 SQLite 日志过滤部分流式 payload，并批量提交；对话期间抽查的近期窗口也没有找到目标增量。该结果不能泛化为所有版本都没有任何增量，但不足以支持将 SQLite 当作等价实时来源。交互式 CLI 的 `codex-tui.log` 也不能直接当作 Desktop app-server 的日志接口。

因此，本轮未选择路线一的依据是已有方案可继续复用、替代路线尚未验证且内容落盘边界改变，**不是“文件缓冲必然使实时显示不可行”**。

依据：[官方日志说明](https://learn.chatgpt.com/docs/config-file/environment-variables#diagnostics)和[现有数据来源说明](../01_initial_experiment/data-sources.md)。

## 5. 接入周期比较与最终选择

| 维度 | Monitor 运行时接入，退出时恢复 | 首次启动接入，卸载前在 App 内恢复 |
| --- | --- | --- |
| 生效周期 | 由 GUI / 产品运行状态决定，频繁启停时多次设置、恢复 | 首次配置后保留，用户可主动恢复并再次配置 |
| 首次接入 | 已运行且未接入的 Codex 仍需重启 | 同样需要重启一次才能取得新环境 |
| 日常启动顺序 | Monitor 先运行最顺畅；未接入的 Codex 先启动时可能需重启 | 接入生效后，打开界面通常无需关心顺序 |
| 临时打开看板 | 当前实例已带桥接时可以重连，否则需等待重启 | 已经经包装器启动的 Codex 可以直接连接采集器 |
| GUI 退出 | 恢复后续启动环境；已运行实例仍保留旧环境和桥接 | 停止采集、保留配置与必要桥接 |
| GUI 崩溃 | 需要独立 helper 恢复外部环境 | 保持接入是预期行为；仍需保证包装器可用 |
| 正常卸载 | 正常退出已完成部分恢复；仍需清理自身文件与旧进程依赖 | 在 App 内恢复与安全清理，再手动删除 App |
| 直接删除 App | 未运行且已恢复时影响较小；运行中删除仍需处理 | 启动脚本回退原 CLI，保留备份以便重新下载恢复；不自动完整清理 |
| 日常实现复杂度 | 需处理每次启停的配置所有权、崩溃恢复和旧进程 | 状态更集中；与现有实现接近 |
| 完整可靠性工作 | 启停、异常恢复、连接续用、安装与卸载 | 稳定入口、App 缺失回退、重装识别、主动恢复与安全清理 |

两者都能在用户执行恢复 / 清理流程后支持正常卸载。接入配置保留不要求采集器常驻；运行时接入也不自动保证退出后没有遗留文件。

**最终选择首次启动自动配置，App 内提供“配置 / 恢复配置”，恢复后手动删除 App。** 不实现退出即恢复，也不增加负责删除检测或自卸载的常驻 Helper。早期讨论过的一键自卸载、拖入废纸篓后自动完整恢复均被这一选择替代。关闭面板、退出、恢复配置和删除 App 是不同动作。

## 6. 选定方案的生命周期约定

### 6.1 安装与接入

目标是首次全新启动由 App 完成发现 Codex、检查兼容性、保存原值、准备运行文件、应用接入配置与检查健康状态；之后可以主动恢复并再次配置。提供默认开启、可关闭的登录启动选项。重复配置 / 重装不覆盖尚未恢复的原始记录，中途失败应回滚本次已经完成的更改。

当前 [integration.py](../../src/codex_progress_monitor/integration.py) 已有包装器、LaunchAgent 和环境备份基础，但不是完整事务式安装器。它目前管理的四个 Desktop 启动变量为：

| 变量 | 当前接入值 |
| --- | --- |
| `CODEX_CLI_PATH` | 生成的 `codex-observed` 包装器路径 |
| `CODEX_APP_SERVER_FORCE_CLI` | `0` |
| `CODEX_APP_SERVER_USE_LOCAL_DAEMON` | `0` |
| `CODEX_APP_SERVER_WS_URL` | 空字符串 |

包装器还在自己的 CLI 子进程环境中设置日志参数。当前不修改 Codex App 安装包、自带 CLI 二进制、主 App 的模型或审批配置。

本表保留 2026-10-16 GUI 实施前的旧入口源码基线；旧讨论中的 `FORCE_CLI=1` 已非当前代码值。该更新只描述源码，不能据此推断已有 Desktop 的环境已经改变，也不表示相关路由行为已经通过运行验收。GUI 管理的新旧包装入口现已加入 App / Python / 启用检查与原 CLI 回退，仍使用开发机 Python；旧接入型 LaunchAgent 已停用，旧 login-start 已禁用环境写入。

环境只作用于后续新启动的进程。检测到现有实例未接入时，应等待任务安全结束，再提示用户正常重开 Codex；不为接入而自动终止正在执行的任务。采集器已启动也不能替代后端接入检查。

### 6.2 日常使用与退出

- 关闭展开面板只影响显示，菜单栏 App 继续运行。
- 退出 GUI 停止采集，不恢复 Codex 配置，也不终止维持已有通信所需的 bridge / app-server。
- 退出期间可能形成观测缺口，重新打开后不伪造连续速度、完整累计或完整阶段计时。
- 当前 CLI 基线由 `KeepAlive=true` 的 LaunchAgent 常驻采集；单独停止进程可能被重启。GUI 实施要适配这一机制，使“退出停止采集”真实生效。
- 登录启动默认开启且可关闭，不能由旧启动脚本反复重新配置或拉起已退出的采集器。
- 重新打开 GUI 时复用或按需启动唯一采集核心，不创建第二套同 runtime 采集器。
- 恢复后再次打开 App 保持未接入，只有主动点击“配置”才重新接入；首次全新启动以外不无条件自动配置。

### 6.3 App 内恢复与手动卸载

App 内“恢复配置”应撤销自身接入并安全处理自身资源。用户随后可以保留 App 再次配置，也可以手动删除 App：

1. 防止旧启动项继续重新应用接入配置，停止对应采集服务。
2. 仅恢复当前仍与 Monitor 安装值一致的配置，保留用户后来改动的值。
3. 原先不存在的变量恢复为未设置，原先存在的变量恢复原值；发行版要验证空字符串与未设置的精确区分，不能仅凭历史备份推断。
4. 已运行的 Desktop 持有旧环境，恢复外部配置不使它立即切换入口。后续新启动才使用原配置。
5. 等仍依赖旧入口的 Desktop 及 bridge / app-server 退出后，再删除包装器和运行依赖；不能仅以“当前没有活动任务”判断可安全删除。
6. 清理不再需要的 Monitor 接入启动项、运行文件及缓存，不删除 Codex 的登录、聊天、数据库或用户后来的设置。恢复依据仅在对应步骤已经成功、不再需要重试时移除。默认恢复保留少量 App 设置与已恢复标记；可选“清理本机数据并退出，用于卸载”，在安全完成后移除自身本机数据与启动注册并退出。

当前 `uninstall` 已能恢复仍由 Monitor 管理的环境、移除对应 LaunchAgent 并停止采集器；它不等于已经删除全部运行文件和依赖，也没有 GUI 恢复状态机。第 5、6 项及完整安装失败恢复仍需要实现与验收。

若 Codex 仍在运行，GUI 显示“配置已恢复，等待 Codex 退出后完成清理”，由打开的 App 等待；提前退出则下次打开继续。该交互已确认，不能假设有常驻卸载 Helper 代为完成。清理失败时保留恢复记录与待处理状态，不把“配置已恢复”误报为“所有清理已完成”。

用户选择清理本机数据并退出时，须等安全清理完成后再删除已恢复标记；全部清理后的再次打开按首次启动处理。未选择时保留已恢复状态，避免下次打开自动重新接入。

正常卸载的约定是先在 App 内恢复与安全清理，再手动删除；直接删除不承诺自动完整恢复或立即清理。清理范围不包括抹除操作系统维护的全部历史记录。

### 6.4 无常驻 Helper 的误删兜底

用户已选择使用普通启动脚本兜底，不新增删除监听、恢复或自卸载用的常驻进程。已有 bridge / collector 是监控核心，不因这一选择而取消。

需要覆盖两个执行入口：

| 入口 | 目标行为 | 边界 |
| --- | --- | --- |
| 配置 / 登录入口 | App 缺失或接入未启用时，不再应用 Monitor 配置 | 不再写入不会自动撤销当前会话或已有 Desktop 中的旧值。旧登录脚本不得反复覆盖用户刚完成的恢复。 |
| Codex 调用的包装脚本 | Monitor App / 必要入口缺失或接入未启用时，直接启动原版 CLI | 保留必要参数和 stdio 行为，不依赖已删除 App 内的 Python，不额外启用 Monitor TRACE。 |

```text
Codex 调用 App 外的轻量启动脚本
    ├─ Monitor 可用且接入已启用 → 启动现有桥接
    └─ App / 必要入口缺失，或接入未启用 → 启动原版 CLI
```

脚本与备份存放在 App 外的固定用户目录，回退分支只依赖系统工具。需要校验真实 CLI 入口，避免回退指回包装器；原 CLI 不可用时明确报错。该检查发生在启动前，不把已开始通信后的任意故障都当成可无条件重启或重放的情况。

兜底在下一次脚本被调用时执行，不是持续删除检测。它改善误删后的启动可用性，不等于自动恢复全部变量、处理已有进程环境或清理全部残留；shell 回退已通过隔离进程验证，日常安装未做误删循环。

### 6.5 重装恢复与升级

未恢复就删除 App 的情况下，原始备份应保留；用户重新下载后可以点击“恢复配置”。新 App 先识别固定目录中的原备份和接入状态，不能因自动配置、重新生成入口或升级而覆盖恢复依据。恢复成功后的下一轮配置可以记录新的基线。

Monitor 升级不能丢失原备份；Codex 升级后检查真实 CLI 入口的有效性。恢复接入时不把旧版 App / CLI 备份覆盖到已经升级的 Codex 上。App 被移动、暂时替换或删除都不触发破坏性自动清理，正常使用时的重新定位方式待实施设计。

## 7. 后续验收范围

当前决策不要求继续验证替代采集路线。当前先在本机运行，具体需求与待执行验收见 [产品需求](requirements.md)：

- 本机 GUI 可运行；未配置、已配置待重开、已接入、断连与已恢复等状态可区分。
- 多 Thread / 子代理总速度去重与覆盖质量正确，原有用量和推理均速语义不退化。
- 配置失败、重复配置 / 重装、原有非默认值、空值 / 未设置、用户后续改值都能正确处理。
- GUI 退出真实停止采集，登录启动可关闭，不因旧 KeepAlive 重启；不强制结束 Codex 任务。
- 先恢复后手动删除流程可完成；运行中恢复不提前清理依赖，未完成状态不能显示为全部完成。
- 默认恢复后重开保持未接入；可选彻底清理完成后退出，重新打开按首次启动处理。
- 仅删除 App 包后启动脚本在缺少 Monitor / Python 时仍可回退原 CLI；重新下载可识别旧备份并恢复。

全新机器免 Python / pip、词表离线完整性、签名、公证与 GitHub Release 发布另属后续发行验证。本机运行不代替这些证据，也不证明全部 macOS 26+ 设备兼容。
