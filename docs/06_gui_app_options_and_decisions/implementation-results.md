# GUI App：实施结果

日期：2026-10-16。本机原生 GUI、Python 管理服务和回退入口已实现；已完成隔离管理流程、本机迁移、日常采集启停及正式恢复后再接入闭环。用户已完成降低透明度开关对比并恢复原设置，本轮本机交付完成。以下按证据层级记录，不宣称所有路径均经过日常使用验证。

## 1. 产出

- `macos/`：macOS 26+ Swift Package；SwiftUI 面板、AppKit 菜单栏与 popover、原生 Liquid Glass 控件、中文资源表。模型与生命周期控制器可独立测试。
- `bin/build-gui` / `bin/run-gui`：本机 `.app` 构建与启动；显式保存 Python、源码、runtime、数据目录与构建指纹，使用本地 ad hoc 签名。
- `overview.py`：从独立活动生成流汇总，排除镜像与历史均速；区分完整、部分与不可用。明确父子关系，拒绝冲突和循环。
- `app_control.py`：准确备份、串行管理、配置失败回滚、逐项恢复进度、延后清理、旧 TUI 迁移、持久恢复意图与可选卸载清理。
- `app_session.py` 与桥接 / 采集器扩展：有界 GUI 心跳、停止与恢复观察、缺口标记、桥接身份登记。原有 CLI 看板继续可用。
- App 外系统 shell 包装器：缺 App、Python、源码入口或启用标记时 `exec` 原 CLI；保留参数、stdio 与退出码，不额外开启 TRACE。旧绝对入口也升级为相同回退脚本。

运行步骤见 [本机使用](usage.md)。当前使用开发 Python，不是免环境发行包。

本机状态与已加载身份的精简记录见 [local-validation.json](local-validation.json)，不包含聊天正文、完整参数或用户输入。

## 3. 本机旧备份的迁移依据

旧版备份把四个变量的原值全部存成空字符串，丢失了“未设置”与“存在但为空”的区别。用户确认这些接入变量由此前 TUI Monitor 开发引入，因此本机将这四项恢复目标记为“原先未设置”。这不是把当前 TUI 的安装值当作原值，也不是向所有用户假定默认值。

迁移前四项当前值与旧备份的 `installed` 完全一致。迁移时保留旧原件，并在 `integration.json` 内保存旧记录、路径及 `user_confirmed_monitor_introduced_unset` 的解释。旧备份原件 SHA-256：`70f1fe8b316f9e97d79c2c9a10a5c850c0b838f219b83e775a733fe0c1e82ed1`。后续正式恢复已完成，旧运行文件按归属清理；重新配置准确取得四项均未设置的新基线，不再导入旧记录。

其他旧安装若有相同歧义，默认拒绝猜测，必须先取得其原状态依据。新安装精确区分未设置和空字符串。

## 6. 重开后的日常验证与恢复闭环

用户正常重开 Codex 后，新 bridge 模块指纹与工作区一致，旧版本提示消失。本机采样 450 个快照，其中 20 个快照同时有两个独立生成流、两个活动聊天且覆盖完整，合计最高约 160.3 t/s；这是一次有限实际重叠窗口，不是吞吐基准。

正式 GUI 退出后，collector、socket 和会话停止；同一 bridge 与原 CLI PID 保持存活，stdio 的三个 Unix 连接保持不变，仅观察连接消失。重开 GUI 后观察连接恢复，业务通信未中断。发现并修复了“重连缺口先于 Thread 身份”导致新加入聊天未保留缺口的问题；93 项相关回归通过，新 collector 已加载修复，本机活动聊天的缺口也已验证保留，新回合清除缺口有协议测试。

用户明确批准隔离目录后，实际点击清理退出：测试原环境恢复、数据目录删除、App 进程退出。再次打开按首次启动自动配置，新备份准确保留原测试环境；验证结束后测试数据已清理。测试使用隔离环境与服务，不以此声称删除了日常数据或注销了正式登录项。

正式安装通过原生按钮执行普通恢复后，四个启动变量准确回到未设置；GUI 等待 Codex 退出后清理，并禁用重新配置。用户正常退出并重开 Codex 后，状态变为 `restored`，旧 runtime 已清理，保留 `restored: true` 与原登录偏好；GUI 显示“已恢复 · 点击配置可重新接入”，没有自行重新接入。

本次临时验收协调进程未跨 Codex 退出存活，未执行预期的自动重新配置；其结果文件停在等待阶段，不能作为后续成功证据。这不影响已经由 GUI 完成的恢复和清理，也没有引入产品 Helper。恢复后已实际点击正式 GUI 的“配置”，新安装 ID 与旧代次不同，四项备份均为未设置，当前安装值逐项匹配，`restored` 变为 false，collector 正常启动。Codex 先于这次重新配置启动时，界面如实提示等待接入。

用户随后再次正常重开 Codex，新后端已连接；原生面板显示“已连接”、当前真实聊天与活动，并已观察到完整覆盖的 `0 t/s`。2026-10-16 08:59 UTC 的只读核对确认：快照年龄约 0.37 秒、GUI 会话心跳有效、两个已连接 bridge 均含 `app_session`，bridge 与 collector 的全部加载模块指纹匹配当前源码，GUI 构建指纹也匹配当前源文件。随后出现新后端尚未关联的事件时可用性会回到未知，不据一次零值宣称任意时刻完整覆盖。最终重新接入的精简证据位于忽略目录 `.local/gui-tests/final-reconnection.json`，正式记录汇入 `local-validation.json`。

## 7. 降低透明度的手动检查

用户报告执行降低透明度对比后 UI 没有明显区别，并明确确认“已对比并关回”。这项证据来自用户手动检查；助手随后只读核对的系统 API 为 false，设置中的“降低透明度”也为 off，与已恢复原状态一致。

主面板使用 `.background(.background)`，玻璃效果仅用于左上角小图标及恢复面板的确认按钮，因此整体变化较小符合当前实现。本项不用于证明不同屏幕、其他系统版本或全部辅助功能设置的兼容性。
