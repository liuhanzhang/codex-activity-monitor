# 菜单栏状态滞留与部分观测排查

日期：2026-10-23。用户反馈：对话期间出现 `Partial observation`，可见回答结束后，菜单栏仍依次显示思考、速度，之后才停止。用户确认问题位置是菜单栏；没有给出具体延迟秒数。

**后续修正：用户再次反馈原症状仍然存在。本文证明两个局部缺陷的修复，不代表完整用户症状已解决。继续排查见[回归调查](status-regression.md)。**

## 已确认的问题

1. **已结束的未关联输出仍阻止全局速度。** `Engine.pending` 同时承担等待身份关联和判定实时覆盖的职责。即使收到相同 item 的 `response.output_item.done`，或者明确列出该 item 的 response 结束事件，队列仍要保留到约 10 秒超时，`overview` 又将整个队列视为未知的当前生成。
2. **状态变化经过两级秒级刷新。** 采集器约每秒发布快照，GUI 约每秒读取一次；这会叠加可见延迟，短暂阶段也可能到其实际结束后才被显示。仅有用户描述和刷新路径，不能断言此前每次延迟的准确时长。

本机限时诊断只保留事件类型、身份和时间，不保留正文、工具参数或结果。第二个 60 秒窗口捕获了 60 条新到达的未关联事件，属于 2 个模型 item；二者均明确结束。它们没有可验证的聊天归属，不能按时间邻近推定其属于主聊天或自动审核。该窗口中 356 条新到达事件从原始观察到进入 Engine 的中位延迟为 0.487 ms，最大 8.933 ms；更老的缓存回放排除在该统计之外。该结果没有显示持续的 bridge 传输堵塞，也不证明其他时间没有阻塞。

## 修改

- 将等待身份关联的保留数量与仍可能活跃的未关联生成数量分开。明确结束的输出不再阻止当前总速度，身份恢复队列仍受原有容量和时间上限约束。
- response 结束只作用于同一 backend 下明确列出的 item。其他未知生成继续使总速度不可用。迟到身份恢复时重新应用已知的结束事件，防止已结束的输出重新变成实时生成。
- 采集器每约 250 ms 计算状态。菜单模式、覆盖、活动聊天或回合状态变化时发布；仅数值变化继续约每秒发布。历史读取调度仍约每秒，不增加其频率。
- GUI 监听快照所在目录的文件系统通知，以兼容快照的原子替换；保留每秒刷新用于时钟新鲜度和恢复。读取使用请求代次，旧读取不能覆盖新结果；退出时取消监听。
- UI 诊断增加快照发布时间，用于量化快照发布到菜单栏更新的延迟。诊断为显式启用的开发入口，验收后关闭。

相关文件：`engine.py`、`overview.py`、`runtime.py`、`collector.py`、`DashboardStore.swift`、`SnapshotUpdates.swift`、`Main.swift`。本次没有更改 JSONL 的历史权威地位或速率口径。

## 验证

- 新增 3 项 Engine 回归：未关联输出结束后立即恢复覆盖、response 成员范围、backend 隔离；同时验证迟到身份恢复不重新产生实时速度。修复前观察到覆盖仍为 `partial`，修复后通过。
- 新增 2 项运行时回归：数值刷新节流与状态变化优先发布；真实隔离 collector 在刚发布思考状态后接收 turn end，必须在 0.75 秒内发布空闲，无固定等待旧的一秒周期。
- 新增 1 项 Swift 回归：真实原子替换快照文件，菜单状态连续跟随“思考 → 空闲 → 思考”，每次状态切换在 0.7 秒截止时间前出现。单独执行整项约 0.05 秒。
- Python 针对性回归共 175 项通过：Engine 33、Overview 9、菜单投影 12、Usage 30、Reconciliation 40、Runtime 24、Timeline 21、Localization 6。
- Swift 默认回归 79 项通过；本机 GUI 构建、ad hoc 签名、语言资源检查和 whitespace 检查通过。
- 新日常 GUI 与采集器已重载，GUI 构建指纹和采集器源码指纹核对通过。新 GUI 的 31 个不同快照样本中，快照发布到 GUI 更新的中位延迟为 14.034 ms，最大 211.050 ms。该统计只覆盖发布后的读取与呈现状态更新，不包括模型生成、事件到达、采样和屏幕实际绘制耗时。
- 诊断原始元数据及运行结果留在 Git 忽略的 `.local/diagnostics/status-lag-20261023/`，不提交真实会话信息。

## 边界

真实未知生成、首次 token 计数尚未完成或跨采集器重载的观测缺口，仍可能显示部分观测或 `—`；不会为了显示完整而清除依据。本次重载跨过当前回合，因此当前回合的缺口仍按原规则保留，完整新回合需要自然使用确认。

本次没有实现独立 GUI IPC，也没有移出采集主循环中的阻塞磁盘写入。文件通知改善刷新延迟，不解决磁盘卡住时的根本隔离问题。没有将一次受控回归或短时本机诊断当作长期自然使用验收，也未提交或推送。
