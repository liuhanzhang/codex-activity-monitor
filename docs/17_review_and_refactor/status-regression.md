## 本次确认并修正的缺陷

Swift 聊天列表只排除明确的 `ephemeral=true` 会话；Python 全局速度和菜单状态却统计所有线程。因此一个已经从聊天列表隐藏的临时任务，仍可使主聊天结束后的菜单栏依次显示“思考 → 速度 → 空闲”，也可用它的观测缺口使正常聊天的总速度不可用。

修正：`overview` 与 `menu_presentation` 共用明确的临时会话边界，排除 `ephemeral=true`。标记缺失或为 false 的线程、普通隐藏聊天和真实子智能体仍保留既有语义；原始线程观测也保留在快照中。没有按名字、模型、时间邻近或不在聊天列表中来猜测任务用途。

3 个新增回归覆盖主聊天完成后临时任务继续思考／输出、临时输出不能遮蔽正常聊天的思考状态、临时流及观测缺口不污染总速度；同时验证未知分类仍参与聚合。修复前菜单回归出现 3 处失败，修复后菜单 14 项、Overview 10 项通过。已有隔离配置中的真实 `thread/fork` 元数据查询也确认，生产协议会明确返回 fork 的临时标记；该查询没有运行模型或续写日常聊天。

用同一临时任务 fixture 驱动 `6314547`，CR 前版本也会出现这组错误状态。因此这是已确认的独立缺陷，仍不能宣称它就是用户认为由 CR 引入的全部回归。

后续自然窗口捕获到明确标记为 `ephemeral=true`、`threadSource=composer_predictions` 的真实后台任务。主回合结束后，当前 GUI 在 +107 ms 绘制空闲，并在该后台任务运行期间保持空闲；相同输入的 CR 前引擎则在 +0.87 s 再次判定工作，随后依次判定思考、短暂不可用、生成，直到 +11.89 s 才空闲。这确认了临时任务污染菜单状态的真实路径和该修正的效果。主回合本身仍跨过重载，且这里的后台运行时长约 11 秒，不能把此样本写成用户描述的每次约 2 秒延迟已全部解决。

## 下一次自然对话的诊断

日常 GUI 已启用限时开发诊断，区分状态更新 `tick` 与首次绘制该模式的 `draw`。`draw` 表示 AppKit 绘制回调完成，不等同于物理屏幕呈现时间。
