# 剩余工作与建议顺序

更新：2026-10-23。依据当前工作区、系统 CR 和后续菜单栏延迟修复整理。这是后续工作的建议顺序，不表示这些项目已经实施；本轮讨论不继续修改产品代码。

已完成：CR 中已确认的身份关联、详情异步契约、查询校验、恢复元数据、快照写入异常、失效缓存与过时 UI 等修复及局部拆分；后续菜单栏修复解决了两个局部缺陷，但用户报告的完整结束延迟仍在[继续调查](status-regression.md)。应优先定位这次回归，再推进下面的新重构。短时采样和受控测试不代替完整新回合、长期自然使用及发行验收。

## 0. 固化当前基线与语义

开始下一轮结构改动前，先将当前变更固化为可审阅、可回滚的本地基线，并补一次完整新回合的菜单栏验收。本次提交只包含现有修正与文档，不包含下述工程工作的后续实现，未推送。

尤其需要按用户已明确的原则复核 CR05：**Codex session JSONL 是历史权威，实时观察负责当前、尚未落盘的补充和实时速度。** 旧历史缓存必须随当前 JSONL 更新或失效；不能把历史和实时设计成两套并列历史来源。

本轮新增的“历史来源消失后，保留独立实时完成”的兜底还需要评估、收敛；它不是修复旧历史缓存失效所必需。这里优先确认产品规则，再删除不需要的状态和分支。CR05 的替换／截短复现属于隔离边界场景，优先级已校准为 P2，不推定日常已完成历史频繁重写。

完成标准：正常历史以当前 JSONL 为准；实时补充有明确退出条件；源不可读、源确实变化、尚未落盘分别有明确结果；重载不补造连续观测或历史实时速度。

## 1. 统一子进程执行的可靠性

范围：`BackendClient`、`QueryProcess` 及其调用边界。

- 并发读取 stdout／stderr，限制输出容量。
- 按操作定义截止时间，统一取消、退出清理和错误返回。
- 处理子进程忽略 SIGTERM 的情况，只管理本次创建的进程。
- 用写满 stderr、忽略终止、取消与自然退出竞争等场景验证。

理由：改动边界相对独立，先让启停与查询失败能够结束，便于后续排查 IPC 迁移中的问题。这不是 IPC 的硬性技术前置条件。当前风险来自代码路径，尚未复现日常管道互等或无法终止。

完成标准：输出压力、超时和取消都有可控结果，不无限等待、不留后台执行任务，也不把旧结果应用到新选择。

## 2. 完成实时通信与持久化解耦

这是剩余主要架构工作。先确定一个小而明确的本地状态订阅协议，再实现 GUI／collector 的连接、断开和恢复。

- GUI 从实时通道接收内存状态；进程所有权、通信健康、恢复存档分别判断。
- 连接后发送完整状态，后续更新合并并限频，慢消费者使用有界缓冲。
- 快照序列化和写入离开采集／通信关键路径；恢复存档单独安排保存策略。
- 继续保持 JSONL 原始详情和独立时间线元数据的职责，不另存一套完整聊天正文。
- 移除已被实时通道替代的生产 GUI 文件通知和常规轮询；保留必要的恢复与只读 fixture 路径。

完成标准：故意阻塞或拒绝存档写入时，事件处理和实时 GUI 仍更新；GUI 暂停读取时缓冲不持续增长；两端重启、断连、正常退出均有明确行为，重连不抹掉真实观测缺口。

本次延迟修复只是状态优先发布和文件通知，尚未达到这个标准。慢磁盘的运行影响仍需故障注入验证。

## 3. 给详情分页增加稳定的来源版本

当前已校验身份和偏移，但同一活动的源内容在两页之间变化时，还不能保证拼接的是同一版本。

完成标准：响应和后续请求携带可稳定比较的内容／section 版本；版本变化时拒绝旧页并明确重新加载，避免静默拼接。版本不能依赖每次 CLI 调用随机创建的 provider generation。

理由：这属于展示内容的一致性，工作范围比传输改造小，适合在运行通道稳定后独立完成。

## 4. 做长期规模测量，再落实资源预算

覆盖长 JSONL、多聊天、持续工具输出、晚到事件、反复重连和慢消费者。测量峰值内存、索引增长、tokenizer 待处理任务和状态处理延迟。

按结果约束 RolloutIndex、活动身份、待计数文本及 GUI 分组投影的成本。不能直接丢弃完成身份后，又允许晚到事件重新打开活动；应明确保留或失效策略。GUI 分组索引、缓存等性能修改以测量结果为依据。

完成标准：有明确的资源预算、受控压力回归和自然使用记录，耗尽预算时保守降级而不是无限增长。当前没有证据把这些潜在增长点全部称为已发生的内存泄漏。

## 5. 继续收紧类型与职责

优先为公开读接口、持久化记录和 IPC 边界建立明确类型，减少同一字典跨协议、领域、展示层流转。新 IPC 类型随第 2 项一起定义；更全面的 Engine 拆分、命名和格式整理放在核心链路稳定之后，按修改范围推进。

完成标准：新贡献者能追踪一个状态的输入、所有者、终止和展示路径；模块边界有明确契约。无需以文件行数或一次全仓机械重排作为完成标准。

## 并行推进的发行准备

以下工作无需等全部结构优化完成，但属于公开发行的前置条件：

- 从干净 checkout 验证最低支持版本，并实际执行 GitHub CI。
- 做不依赖开发者源码／venv 绝对路径的发行包，验证签名、公证、安装、更新、卸载和恢复。
- 确定许可证，盘点拟发布素材及来源；复核公开文档和 Git 历史中的私人数据。
- 验证当前 Codex 版本、升级／崩溃恢复、Remote、旧版本迁移、VoiceOver 和多显示器。

许可证与素材分发范围需要维护者决定；本计划不替代该决定。可先发布范围清晰的预览版，不需要把所有可维护性优化都升级成首次发布阻塞项。

建议执行顺序：**当前基线与语义 → 子进程可靠性 → IPC／持久化隔离 → 分页版本 → 长期规模 → 渐进结构整理**。发行准备同步进行，在正式发行前单独验收。
