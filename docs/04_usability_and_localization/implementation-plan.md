# Monitor 易用性与多语言准备：实现计划

日期：2026-10-13。状态：P1–P6 已实施并完成相关验收，以下保留实施步骤。结果与运行边界见 [实施结果](implementation-results.md)。

产品需求与验收条件见 [需求文档](requirements.md)。本计划从现有工具生命周期实现上调整展示与名称解析，采用针对改动的验证范围。

## 1. 实现策略

按“语义消息与文案资源 → 名称提取 → 统一渲染 → 刷新与设置 → 有限验证”推进。先让状态逻辑摆脱中文字符串，再修改最终显示，避免文案变化意外改变生成速度、可见活动或断连处理。

新增结构化消息与名称元数据时保留原有身份和必要兼容字段。采集 / 指标的约 250ms 内部节奏继续保留；终端和连续快照输出的定时刷新改为 1Hz。

MCP 取名优先利用已保留的 `appContext.appName/actionName` 和有可靠身份关联的展示元数据，按统一规则选择最面向用户的名称。只有现有通信中确实出现可靠目录元数据时才补充被动消费，不主动调用 app-server 获取名称，不设置手工产品别名或服务特例。

## 3. 分步计划

### P1：建立语义消息与中文资源

1. 枚举实际面向用户的文案：表头、活动、完成 / 失败状态、连接与空状态、并行数量、页脚、详情上下文、CLI 提示和时间表达。内部诊断内容和用户原文不作为翻译目标。
2. 在 `i18n.py` 建立稳定消息 key 与格式化接口，中文资源提供当前交付所需的全部 key。动态名称、数量和时间通过参数传递。
3. 将 `activity_label()` 的职责拆为“生成语义描述”和“渲染描述”。主行、详情、最近完成项共用名称数据，但按各自活动状态渲染。
4. 将 `presentation()` 中对“连接中断”“状态暂不可用”等中文标签的比较改为连接 / 可用性等语义条件。`PHASES`、collector 恢复与 display 过期分支也统一接入语义描述。
5. 新快照增加结构化消息，旧 `display_label/phase_label` 保留中文兼容输出。语言切换不重算活动身份、主活动选择、耗时或速率。
6. 将名称解析与新增文案模块纳入相关进程的 `source_identity()` 依赖清单，确保后续加载检查不会漏掉本轮改动。

建议的消息形状如下；具体字段使用一套固定结构，避免每个调用点各自拼字符串：

```json
{
  "display_message": {
    "key": "activity.preparing",
    "params": {"target": "python"}
  }
}
```

名称元数据与消息 key 分开保存。MCP 可以保留 `product_name`、`tool_display_name` 和 `name_source`，需要渲染时组合为 `产品展示名 · 工具展示名`。可诊断的原始 `server/tool/namespace` 不用于比较展示文案。

兼容策略：新看板优先读结构化描述；遇到旧快照时利用已有 kind、status 和工具元数据尽量重建，信息不足时使用中性状态。可能带命令参数的旧诊断标签不直接用于活动展示。旧快照缺失的产品展示元数据无法补造，该边界在使用说明中注明。

完成条件：改动后的状态逻辑不依赖中文文案；现有准备、运行、暂停、断连、未知与生成速度规则可继续验证。

### P2：实现命令名提取

1. 增加独立的 `command_name()` 一类纯解析函数；保持 `command_summary()` 原有诊断用途，避免直接改变桥接摘要导致兼容问题。
2. 接收字符串、已有 argv 形式和命令预览中的有界字面量。准备阶段与真实命令事件复用同一套名称规则。
3. 识别完整首个 token、引号、环境变量和已知启动包装；递归剥离可安全识别的 `sh/bash/zsh -c/-lc`。对 `env`、`sudo` 等包装只支持明确的选项形状，不知道选项如何消耗参数时停止剥离。
4. 有限识别简单前置 `cd ... &&` 或 `cd ...;`，保留其后的首个实际命令。多个实际命令或管道的主行只取首个可靠名称；不据此声明后续命令已运行。
5. 控制操作符只在引号 / 字面量之外识别；沿用有界扫描与保守回退，不实现完整 shell AST 或执行任何代码。
6. 在参数流和真实生命周期元数据更新时补齐 `command_name`。首个 token 尚未完成、动态命令或摘要已截断时，保持通用展示；真实名称后来到达只更新名称。
7. 列表与普通详情改用命令名，原有摘要留在诊断字段；不通过详情再次暴露参数。

完成条件：需求示例中的路径、flag、参数均不进入可见名称；参数流补齐名称不会把准备活动提前改成运行。

### P3：解析 MCP 产品与工具名称

1. 在 `_tool_metadata()` 消费已过滤的 `appContext.appName/actionName`，做长度限制和显示控制字符清理，关联到当前活动。
2. 解析直接调用的 `server/tool/namespace` 和 Code Mode 识别出的 `mcp__...` 名称。不要假设所有名字都只有一个简单的服务段；保留可区分的服务 / 应用作用域。
3. 建立一套通用的元数据名称选择器，产品与工具均按“面向用户的展示名称 / 标题 → 提供方声明的名称 → 清理后的协议短名”取值。不维护手工产品别名表，不为特定服务改名。
4. 工具标题缺失时保留真实工具名，不根据描述自行概括操作。统一处理名称长度与控制字符，保留可区分的身份作用域。
5. 如果现有 Desktop 通信或可复用记录包含可靠的产品、插件、服务或工具目录展示信息，再检查其身份、过滤与缓存路径；只保存名称和关联所需字段，按后端 / 服务作用域缓存，防止串名。缺少这条路径时，使用调用元数据和协议短名回退，不另加映射特例。
6. 为名称记录来源，便于验证是展示名称、提供方名称还是协议短名回退。名称变化不改变活动 ID、开始时间、完成状态或后台归属。

完成条件：直接 MCP 与生成脚本中的名称均能正确组合；缺少元数据时可读且保守，默认界面不显示 `mcp__` 这样的协议前缀，全部服务按统一规则处理。

### P4：统一活动文案与结果展示

1. 命令与普通工具准备阶段渲染为 `准备中 · target`，确认执行后为 `运行中 · target`。MCP 的 target 包含产品名与工具名。
2. 没有名称时只展示状态；生成结束但执行未确认时沿用中性 `处理中`，不借改文案降低证据门槛。
3. 已结束详情使用名称与独立状态列；最近完成项使用 `刚完成 · target`。失败、停止、未执行和未知结果按真实状态显示。
4. 修改文件、思考、搜索、审核、压缩等已有专门动作保持原语义，统一迁入文案资源。
5. 外层 Code Mode 仍不重复占据已经有实际内部活动的主行；并行数量、hook 隐藏与 Desktop 操作提示分工沿用原实现。

完成条件：列表、详情与最近完成项的文案一致，不出现已经完成的活动仍被称作“运行中”。

### P5：调整刷新与耗时

1. 将 `seconds()` 改为本地化的整秒格式：不足一秒返回空字符串；其他已知耗时按 `Ns`、`NmSSs`、`NhMMmSSs` 显示，未知耗时仍为 `—`。覆盖一秒、一分钟、一小时边界，使用真实内部时间并向下取整，不修改活动计时来源。
2. 为 watch 建立单一的定时渲染调度：每秒读取 / 渲染一次快照。Rich 使用显式刷新，避免其后台自动刷新与主循环重复刷新。
3. 输入等待使用下次刷新 deadline 计算超时；选择、展开和语言切换触发即时渲染，`q` 即时退出。避免直接阻塞 `sleep(1)` 导致按键等待。
4. JSON 与非 TTY 连续输出改为一秒间隔；`--once` 行为不变。
5. 保留 collector 的事件消费、指标 tick 和快照节奏。生成速度的窗口、重算预算、估算标记和空流语义不随 UI 频率改动。
6. 检查短活动的完成记录与详情仍可见，不延长“运行中”来补偿主行漏采样；保留过期快照与断连降级逻辑。

完成条件：无键盘输入时定时刷新为 1Hz，主动操作即时响应；不足一秒不显示耗时，分钟 / 小时边界正确，完成耗时冻结。

### P6：接入语言设置与切换机制

1. 用语言注册表声明可用资源。首轮产品资源为 `zh-CN`；添加完整 `en` 资源后自然进入可用列表，不修改状态引擎。
2. 在 runtime 下增加独立的 `ui-settings.json`，只保存设置版本与语言代码，复用 `atomic_json()`；不复用安装 / 卸载备份或 Codex 配置。
3. `watch --lang` 显式参数覆盖本次启动；否则读取保存语言，再回退 `zh-CN`。缺失 / 损坏设置不阻止打开看板；不支持的显式语言给出清楚错误。
4. 预留 `l` 对可用语言循环切换，只有至少两种完整资源时才显示入口。主动切换后立即重新渲染并保存选择；设置无法保存时保留本次选择，不影响采集。
5. CLI 面向用户的描述和提示纳入资源；快照 JSON key、协议身份、品牌名和原始名称保持语言无关。
6. 缺失翻译 key 按统一策略回退中文；通过资源完整性检查，确保后续英文发布时覆盖已注册的中文 key 和模板参数。不要向普通用户展示内部 key。
7. 用测试专用的第二语言资源验证同一快照切换语言；不把不完整测试资源作为产品中的英文选项发布。

完成条件：本轮中文界面使用集中资源，语言选择与保存机制可验证；后续补齐英文资源即可启用真正的中英切换。

## 4. 验证范围

### 4.1 针对改动的回归

| 验证位置 | 重点 |
| --- | --- |
| `tests/test_tool_labels.py` | 路径 basename、完整 token、shell 包装、环境变量、前置 `cd`、复合命令、引号 / 操作符、动态与截断回退。 |
| `tests/test_display.py` | 准备 / 运行 / 结束文案，主行与详情无命令参数，不足一秒留空、整秒和分钟 / 小时边界，过期快照与短活动。 |
| `tests/test_engine.py` 的相关用例 | 分块输入更新名称、真实执行信号、晚到元数据、名称补齐不重置身份 / 时间、完成后不重开。 |
| `tests/test_progress_semantics.py` 的相关用例 | 执行未确认、并行阻塞、后台活动、观测缺口、MCP 启动与生成速度条件。 |
| 新增 i18n / 设置用例 | 消息参数、可用语言、优先级、保存 / 回退、测试资源切换、文案不影响内部状态。 |
| watch 调度检查 | 定时 1Hz、主动按键即时更新、JSON / 非 TTY 频率、退出响应。 |

更新已有断言时同时验证行为，尤其不能只把“准备命令”替换成“准备中”就视为生命周期正确。名称解析用例需要包含敏感参数，确认参数不会进入可见名称。

测试使用现有 `.local/venv` 和 `unittest`。实施时选择上述模块或具体受影响用例运行，不默认重做所有产品实验、全部历史捕获或 87 种事件盘点。

若更改 `events.py`、桥接缓存或快照兼容路径，再补运行 `tests/test_runtime.py` 中对应的过滤、恢复和私有快照检查；只有新增失败或兼容疑点才扩大验证。

### 4.2 有限渲染与运行检查

1. 用固定快照渲染列表与详情，覆盖长产品名、多聊天、未知名称、完成 / 失败、窄终端和中文资源，检查截断与参数隐藏。
2. 在独立临时 runtime 验证 watch 的刷新、按键、语言设置和旧快照兼容；避免为界面测试重启日常 collector。
3. 如需要真实数据，复用一份相关的已有工具记录，或选择短命令和可触发的 MCP 活动，记录最小元数据与渲染结果。
4. 记录未触发的元数据路径与语言边界。源码、合成 / 回放、运行快照和实际终端效果分开报告。

英文资源尚未交付时，只声称中文资源化和语言机制通过验证，不声称英文界面已完成。

## 6. 技术待验证项与回退

这些是实施中的验证任务，不是需要用户补充的产品问题。

| 待验证项 | 检查方式 | 回退 |
| --- | --- | --- |
| 当前直接 MCP 调用是否带 `appContext` | 检查现有记录或最小真实调用是否经过过滤和活动关联。 | 按统一优先级使用其他已关联的提供方元数据或协议短名，不新增服务特例。 |
| 工具目录展示元数据是否在现有链路可被动取得 | 核对已有请求 / 响应、作用域和过滤路径，先验证最小字段。 | 不增加主动请求；后续有依据再扩展元数据支持。 |
| 旧包装器的摘要是否足以识别命令名 | 用旧形状、截断和参数分块用例检查。 | 通用名称 / 状态，等待真实完整元数据，不显示截断路径或参数。 |
| Rich 显式刷新与输入调度是否达到目标 | 独立终端运行观察定时更新及按键响应。 | 保持单一渲染调度，修复实际重复刷新后再验收。 |

计划不以这些元数据始终存在为前提；已有证据门槛与保守回退是必需行为。
