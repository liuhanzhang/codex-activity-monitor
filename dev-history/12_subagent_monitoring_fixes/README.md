# 子智能体监测与展示修复

日期：2026-10-20。状态：F01–F04 已实现，完成定向验证并更新日常 Monitor。诊断源码基线：`728af1e47d84`。实际结果、证据与未验证边界见[实施结果](implementation-results.md)。

## 1. 已确认范围

本章依据一次真实的三子智能体运行、一次已完成子智能体的追加任务，以及随后进行的只读查询和隔离模型复现。修复范围如下：

| 编号 | 问题 | 目标行为 |
| --- | --- | --- |
| F01 | 通信对象混入父子关系；子智能体可能在“最近完成”中成为独立聊天 | 父子层级有明确来源；列表先按主聊天归组，再应用数量限制；子智能体不重复计入主聊天数 |
| F02 | 一个阶段缺少结束记录，覆盖了已经明确结束的轮次状态 | 组显示所选引用范围的轮次结束状态，缺失阶段单独提示记录不完整 |
| F03 | 实际创建、发送消息、追加任务只有普通参数生成标识，缺少协作动作和对象 | 用明确调用关系补充已有阶段的协作展示，保留原阶段身份、轨道与时间 |
| F04 | 未指定具体对象的全局等待显示“对象未知” | 有证据的全局等待显示“等待子智能体消息”；确实缺少对象证据时保留未知 |

**已排除：“最近完成”里默认看不到前轮子智能体。** 当前详情按轮展示，后续没有派发子任务的轮次不应混入前轮活动。用户已经确认这不是问题。本章不改变默认轮次、轮次选择器，不增加会话总览或历史子智能体入口。

## 2. 诊断证据与边界

以下是修复前的观察，不是修复验收结果：

- 实时快照和 `tl.sock` 查询确认主智能体及三个子智能体的显式身份；最初工作轮的完整查询返回 190 个活动阶段，另有 1 个用户输入标记。
- 同一子智能体的初始工作与追加任务均保留自己的 turn ID，并明确引用同一父轮；主聊天视角能够读到两轮活动。
- 三份子会话的已验证 `session_meta` 都含 `source.subagent.thread_spawn.parent_thread_id`，可作为真实父线程身份来源。
- 单独查询子智能体轮次时，给主智能体发消息的关系使真正的主智能体被列成其“子智能体”。
- 主轮已有完成记录，但一个 `exec` 参数生成阶段为 `unknown / missing_item_end`，其详情返回 `not_retained`；整个主组因此仍为 `unknown`。源历史没有保留该输入，不能据此断言 Monitor 丢失了一个原本可恢复的结束记录。
- 本次三个创建调用、两次父级发送消息和一次追加任务具有明确调用 ID，但没有获得专用协作展示；八次等待获得协作展示，其源记录的对象列表为空，原始调用未指定接收对象。
- 后续真实快照中发现一个明确标为 `thread_source=subagent` 的线程进入“最近完成”顶层列表。它不等于证明本次三个子智能体在用户观察的同一时刻全部被单列。
- 直接编译现有 Swift `Snapshot` 模型，复现了回信形成环后父子边被移除、同级子任务过期后剩余子任务被单列、先截取十个线程导致父聊天被排除三类条件。

本轮诊断未取得对应时刻的原生截图，不能据此判断裁切、重叠、键盘或辅助功能是否存在新问题。实现后需要定向原生检查和新的真实运行验收。

完整会话、运行快照、数据库和诊断原始输出不纳入 Git。原始材料当前位于本机 `/tmp/monitor-agent-runtime-comparison.json`、`/tmp/monitor-agent-audit-final-bundle.json`、`/tmp/monitor-agent-audit-detail-checks.json`、`/tmp/monitor-agent-recent-turn-comparison.json`、`/tmp/monitor-agent-recent-model-results.json`；这些是临时定位信息，可能失效，实施前须重新确认并将需要保留的私有证据移到 Git 忽略的本地目录。本章保留必要的脱敏结构、计数和复现条件。
