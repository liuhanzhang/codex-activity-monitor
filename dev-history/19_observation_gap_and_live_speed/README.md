# 历史观测缺口与当前速度展示

更新：2026-10-25。起始代码基线：`1a49f46`。**代码、受控验证及日常 GUI／collector 更新已完成；驻留 bridge 保持旧版本，完整自然回合验收仍待完成。** 实际变更与证据见[实施结果](implementation-results.md)。固定一秒测速口径见[最近一秒的接收速度](../18_engineering_hardening/one-second-speed.md)。

## 问题与已确定规则

原实现的会话 `quality` 会保留本轮曾发生的 `observation_gap`。`overview.py` 因这个标记排除整个活跃会话，`menu_presentation.py` 和 Swift `Snapshot.menuTitle` 又分别限制不完整覆盖的展示。因此，会话的新生成流已有有效速度时，菜单仍可能长期显示 `—`。时间轴可由 JSONL 补充历史事实，不能用其视觉完整性证明实时 token 接收连续，也不应让历史缺口统一否定当前指标。

| 当前情况 | 状态栏 | 会话及时间轴 |
| --- | --- | --- |
| 曾有缺口，当前速度有效，时间轴已有可靠事实 | 正常显示观测速度合计 | 正常展示，不显示当前异常标记 |
| 一部分当前生成流可计量，另一部分不可确认 | 直接显示有效观测值的合计，沿用现有数字与单位 | 只在仍受影响的会话或具体指标处提示 |
| 当前没有任何有效速度读数，且不能确认空闲 | `—` | 说明仍存在的采集、计数或归属问题 |
| 有效观测值全部为零 | 显示零 | 零只代表已观测部分；部分覆盖不能据此认定所有聊天空闲 |
| 已确认没有当前生成流，但仍在思考或运行工具 | 沿用既有思考／执行展示，速度可确认为零 | 不把无生成流当作采集异常 |
| 健康连接下已确认没有活跃或未知工作 | 沿用现有空闲展示 | 不生成异常 |
| 正常新流首次计数尚未完成 | 没有有效数字时显示 `—`，不显示文字占位；如其他流已有数字则显示它们的合计 | 正常采样不作为异常 |

状态栏不增加“已观测合计”、告警前缀或说明文字。历史缺口只保留在内部诊断记录；只有仍造成当前速度不可确认、某段时间未知等问题时，才在受影响位置展示提示。历史问题恢复后，对应当前提示应消失。

## 数据与判定边界

分别维护三类事实，不把一个会话级标记作为全部指标的开关：

1. **历史观测事实**：某时刻中断、丢弃、解析失败，及当时可确认的受影响范围。后续恢复不删除已经发生的事实。
2. **当前速度可用性**：逐条独立生成流判断当前一秒窗口的接收连续性、计数结果时效和身份归属，再汇总可用读数。覆盖是否完整与是否有可显示数字分开。
3. **活动和时间轴可用性**：按该活动的开始、结束、身份和历史来源分别判断。JSONL 可以确认活动完成，但不能补造当时没有收到的 token 或接收时钟。

共享 backend 的未知丢失可以保守影响当时活跃的生成流，但不能推断出错数据来自某个聊天。后续新流或已建立新测速基线的流按当前事实独立判定，不继承整轮历史异常作为永久禁用条件。

## 实施设计

### 生成流恢复

- 新建且身份明确、在缺口后完整接收的流，沿用固定一秒及首包不外推的测速规则，不等待整轮结束。
- 对跨越缺口的旧流，建立新的接收与计数代际，隔离缺口前后的文本前缀、接收位置和窗口结果。清空或失效旧的测速任务引用，迟到结果不能覆盖新代际；原 worker 未完成的内存仍纳入现有预算。
- 恢复依据是明确重新接入并建立连续接收区间与有效计数基线，不能仅因缺口过去一秒、收到了一个 delta 或当前无输出就清除问题。旧流的窗口进入恢复后的连续区间，且计数有效后才能恢复测速。
- 缺失内容不参与回填，不跨 item、来源、计数代际或模型编码混用基线。本地累计 token、历史完整度和官方 Output／Reasoning 用量继续各自保留来源及覆盖边界。
- 接收仍有缺口、文本／时序预算超限、计数失败或身份归属不明的流不贡献数字。不能用零、旧窗口或历史 token 数代替。

### 汇总与协议

- `overview.py` 收集身份明确、连接有效、窗口有效的独立流；去重规则继续基于流身份，镜像行及父子展示关系不能造成重复相加。
- 历史会话 `quality` 不再整行阻断汇总。当前不可用的流与未关联生成事件仍计入覆盖诊断，其他流的有效读数照常贡献。
- 复用 `overview.observed_subtotal` 作为当前观测数字；`generation_rate` 保留完整覆盖合计的原义，`coverage` 继续区分完整、部分和不可用。有有效读数时，展示状态允许为 `ready`，不与完整覆盖绑定。
- 会话的 `generation_rate` 同样取该会话当前可用独立流的合计；增加可选的当前速度覆盖与原因字段，供行内提示使用。历史 `quality` 不直接映射成当前告警。
- 没有有效读数且无法确认当前生成状态时保留 `null`。已确认没有当前生成流（可以仍在思考或运行工具）、健康空闲或有效观测明确为零时才给出零；未知部分不补零。
- Swift 旧客户端仍可按完整覆盖保守显示；新字段采用可选解码，新客户端统一经同一个展示速度入口选取数值，避免状态栏、展开面板和 tooltip 使用不同规则。

### 原生与终端展示

- `Snapshot.menuTitle`、`menu_presentation.py` 和面板顶部数值共同使用当前观测合计；局部异常不再把整个菜单切为不可用。
- 保持现有思考、执行和空闲动效规则。数字可用不证明活动状态明确：当前覆盖不完整或活动未知时可展示数字，但不借此推断空闲或播放需要可靠状态的动效。只有历史缺口且当前已恢复时，不再限制正常状态。
- `progress_state.py`、`ChatRowView` 及终端消费相同的当前速度状态。部分流有效时展示其合计，确有当前问题时在该会话的现有行布局内增加小标记与简短帮助说明；不新增占位行或长期历史警告。
- 时间轴及独立 Activity Viewer 保持按活动证据展示。已被权威历史补齐的活动不因会话历史缺口统一染成异常；仍未知的时间只在对应位置保留提示。
- 全局连接失效、状态过期且没有其他有效观测值时仍显示 `—`，不展示缓存旧数字。无法归属到具体聊天的问题保留在现有全局连接／诊断详情，不猜测告警归属。
- 中英文提示同步维护。现有“部分回合缺少连续观测，暂不显示总速度”文案不再用于仅有历史缺口或已有有效观测数字的情况。

### 缺口来源分类

明确区分会影响生成接收的丢失、已知与测速无关的诊断丢弃、以及无法判断影响的事件。已知无关的日志丢弃保留计数，不自动使所有活跃流失效；不能证明无关的情况继续按当前流受影响处理。

`oversized_diagnostic` 目前只说明丢弃了过长诊断行，没有保留足以确认内容性质的证据。因此不能统一把这类记录忽略；只有在桥接层有足够分类依据时才缩小影响范围。不扩大缓冲上限来掩盖问题，也不删除历史质量记录来获得正常显示。

本次只补充恢复与分类需要的有界原因、时刻和作用范围，不另建完整日志系统。既有 JSONL 保持原样；无法追溯的旧错误不补写为已确认原因。

## 实施顺序与验证

1. 先完善逐流当前窗口判定、恢复代际和有界原因记录，验证迟到计数不会污染恢复结果。
2. 调整会话和 overview 汇总、覆盖字段及菜单状态，再统一 Swift／终端读端和本地化提示。
3. 做针对性回归、隔离 collector 和双语原生展示验证，记录结果后安排日常版本切换。切换时核对 GUI、collector 与相关驻留 bridge 的实际版本；需要新 bridge 才能生效的分类修改不能仅凭磁盘源码宣布上线。

重点验收场景：

- 历史有缺口，当前新流完整有效：该会话贡献数字，菜单恢复显示，无当前异常标记。
- 两个会话或同会话两条流分别正常／异常：只累加有效读数，异常定位到仍受影响位置，正常部分不被屏蔽。
- 缺口穿过旧流窗口：缺口期间不可用；新代际进入完整观测窗口后恢复，旧任务迟到不生效。再次缺口重新进入恢复过程。
- 当前有效观测为零、全部未知、已确认无生成但仍在思考／执行、已确认空闲、首次正常计数、计数结果过期分别展示正确；部分覆盖下零不能触发全局空闲。
- 重复、镜像、子代理及身份冲突事件不重复计数；归属不明的数据不借给已有会话。
- 原始诊断丢弃分类已知无关／影响未知分别处理，不把无法追溯的旧计数当作无害证据。
- JSONL 补齐时间轴而速度仍不可确认，以及速度恢复而旧时间段仍未知，两种情况独立成立。
- 实时连接中断、全局状态过期及恢复不复用旧数字；中英文、状态栏、面板和终端口径一致。

上述规则的代码、受控验收和日常 GUI／collector 切换已完成，具体结果见[实施记录](implementation-results.md)。独立 Preview、隔离 collector 和跨切换的短时实测不代表完整自然回合验收；历史缺口的原始报文来源仍不能追溯为已确认原因。
