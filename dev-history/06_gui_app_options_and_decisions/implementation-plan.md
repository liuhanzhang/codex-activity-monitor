# GUI App：实施计划

日期：2026-10-16。状态：本轮本机实现与有限验收已完成，包含迁移、实际采集启停、正式恢复后再接入，以及用户手动降低透明度对比；各项证据与后续验证边界见 [实施结果](implementation-results.md)。以下保留实施前基线、执行顺序和完成条件。需求及 A1–A12 编号见 [产品需求](requirements.md)，历史方案比较见 [决策总览](README.md)。

## 1. 实施范围与顺序

当前交付一个在本机可运行的 macOS 菜单栏 App：总生成速度、聊天列表与详情、配置 / 恢复、退出停止采集、登录启动、误删后的 CLI 启动回退。目标系统为 macOS 26+，本机通过不等于所有目标设备兼容。

按“只读 GUI 骨架 → 管理状态与数据契约 → 列表与详情 → 配置与生命周期 → 恢复与清理 → 有限本机验收”推进。先在隔离目录与模拟 CLI 中验证管理动作，再迁移当前安装；不为了开发 GUI 直接重启日常 Codex。

- 保留 Python 指标核心和现有 stdio 包装器，不迁移 Rust，不切换采集路线。
- SwiftUI 负责视图，AppKit 负责菜单栏与弹出面板；GUI 读取 JSON 快照，不自行实现分词、用量账本或活动状态机。
- 当前使用本机 Python 环境。PyInstaller、全新机器离线运行、正式签名公证、GitHub Release、Intel / 其他平台交付后续再做。
- 不增加常驻卸载 Helper、HTTP 服务、跨语言 FFI、聊天控制、跳转或长期历史功能。
- 正常恢复保留少量 App 设置；可选清理本机数据后退出，App 包由用户手动删除。

## 3. 技术与目录基线

### 3.1 原生 App

| 部分 | 实施基线 |
| --- | --- |
| 工程 | 新建 `macos/` Swift Package，包含原生可执行入口、可测试模型与资源；构建脚本组装本地 `.app`。P0 若发现必要系统能力不适合该工程方式，再局部改用 Xcode 工程并记录原因。 |
| 菜单栏 | [NSStatusItem](https://developer.apple.com/documentation/appkit/nsstatusitem/button)，图标与单独的数字标题，数字使用等宽样式；1Hz 数据刷新，展开和按钮操作即时响应。 |
| 面板 | [NSPopover](https://developer.apple.com/documentation/appkit/nspopover/contentviewcontroller) 承载 `NSHostingController` 与 SwiftUI；以约 720 × 520 pt 为布局起点，约束在可见屏幕范围内。 |
| 系统材质 | 在适合的容器使用系统 Liquid Glass，验证透明度、对比度、减少透明度设置和浅 / 深色。系统承载有问题时局部调整窗口，不改指标或生命周期。 |
| 生命周期 | AppKit 处理打开、关闭与退出；后台文件读取和管理命令不阻塞主线程。 |
| 登录启动 | 优先验证 [SMAppService.mainApp](https://developer.apple.com/documentation/servicemanagement/smappservice/mainapp)，读取实际授权 / 注册结果。若本地构建方式受限，改用只负责启动 GUI、`KeepAlive=false` 的用户 LaunchAgent；不复用旧采集器常驻脚本。最终只保留一种生效方案。 |

本地 `.app` 放入忽略的 `.local/gui/`，必要的本地签名用于构建验证，不宣称具有公开发行身份。构建与运行脚本必须记录开发 Python、源码根目录和构建身份，不能靠 Finder 继承终端的 PATH 或虚拟环境。

### 3.2 职责与存储

```mermaid
flowchart LR
    D[Codex Desktop] <--> L[App 外的轻量启动脚本]
    L <--> B[bridge 与原版 CLI]
    B --> C[Python 核心]
    C --> S[原子 JSON 快照]
    S --> G[AppKit 与 SwiftUI]
    G -->|一次性管理命令| M[配置与恢复服务]
    M --> R[App 外的原配置备份与恢复进度]
```

- 用户数据根目录采用 `~/Library/Application Support/CodexProgressMonitor/`；运行文件、原始配置备份、接入记录和 GUI 偏好分开。产品不能向 `.app` 包内写运行数据。
- 备份与启动入口位于固定用户目录，不能放入会随 App 包删除的资源目录或当作普通缓存清理。
- IPC 路径在任何接入变更前检查当前 Unix socket 的长度限制。短 runtime 与持久备份根目录可以分开，不能为缩短 socket 路径把唯一备份放入临时目录。
- 已有 `.local/runtime/` 由迁移步骤处理，不能在新目录直接把旧 Monitor 配置记成安装前基线。旧包装器与运行依赖在旧 Desktop 退出前保留。
- 数据目录保持当前用户私有权限；只记录数值、身份、路径、状态和必要诊断，不新增正文、完整参数、用户输入或隐藏推理的落盘范围。

拟新增模块与文件名在实现时可小幅调整，职责不变：

| 位置 | 职责 |
| --- | --- |
| `macos/Sources/MonitorApp/` | App 入口、菜单栏、面板、设置和恢复交互 |
| `macos/Sources/MonitorModel/` | 快照 DTO、可用性、列表投影、状态与命令结果解码 |
| `macos/Tests/` | 数据契约、过期 / 缺失处理、状态转换与管理动作失败的测试 |
| `bin/build-gui`、`bin/run-gui` | 本机构建、组装 `.app` 与显式运行模式 |
| `src/codex_progress_monitor/overview.py` | 独立生成流汇总与覆盖质量，不引入第二套 tokenizer |
| `src/codex_progress_monitor/app_control.py` | 配置、恢复、迁移、暂停 / 恢复采集及持久化事务 |
| `src/codex_progress_monitor/gui_snapshot.py` | GUI 所需数据与同源文案投影，保留语义消息 |

GUI 管理命令使用参数数组调用现有 Python CLI 的 `app` 子命令组，拟包含 `status / configure / resume / stop / restore / cleanup`；一次动作返回带版本、状态、错误码和待处理项的 JSON，人类诊断走 stderr。GUI 每秒直接读取快照和管理状态，不每秒启动 Python 子进程。原有终端命令继续可用。

## 4. 数据契约与展示规则

### 4.1 全局速度

在 Python 核心中完成，GUI 不从 Thread 数字或当前可见行反向推导总速度：

1. 复用逻辑 `home / thread` 身份与当前后端选择规则，再以 `turn / item / kind / part` 等稳定身份识别独立流。同一流被多个活动引用也只计一次。
2. 延用现有上游 / 协议来源选择、序列去重和异步镜像排除。跨后端身份不能确认时降级覆盖质量，不按名称、内容相同或数字相同去重。
3. 统计已接入的独立 `text / plan / summary / tool_input` 生成流，包括后台与子代理流。列表隐藏、父子折叠和最近完成筛选不改变统计范围；已完成流和事后均速不相加。
4. 使用同一次 tick 的单调时钟与既有速度窗口。连接、流状态、分词待处理、观测缺口和身份冲突共同决定可用性。
5. 有后端且观测可判断、当前确认无生成时可给零；没有后端、只剩历史快照或活动流尚不可判断时不能给零。`complete` 只针对已接入范围，不代表所有 Codex 后端。

快照在兼容现有消费者的前提下新增版本化 `overview`，建议字段如下；P2 用契约测试固定最终字段：

```json
{
  "version": 1,
  "scope": "observed_local",
  "coverage": "complete",
  "generation_rate": 24.6,
  "observed_subtotal": 24.6,
  "estimated": false,
  "active_thread_count": 2,
  "known_stream_count": 1,
  "unknown_stream_count": 0,
  "quality": []
}
```

`coverage` 使用 `complete / partial / unavailable`。只有可声明为已接入范围合计时 `generation_rate` 才为数值，否则为 null；有可靠部分流时可单独提供 `observed_subtotal`，没有可用样本时也为 null。

菜单栏数值以一位小数、紧凑单位 `t/s` 起步；正常零值显示 `0 t/s`。部分覆盖与不可用均不把小计冒充总量：菜单栏显示 `—` 并以状态区分，面板说明原因、可用时展示“已观测小计”。编码估算标志与部分覆盖标志分别处理。

### 4.2 聊天、父子关系与本地化

- 复用现有 Thread 字段、活动展示描述和 usage 对象，不在 Swift 中重新判断执行身份、审批状态或用量归属。
- 父子关系只用明确的子代理来源 / 创建事件与 Thread ID 建立；普通 `sendInput`、消息接收者或同项目名称不能证明父子关系。来源冲突或父项未观测时保留为独立项，不强行归树。
- 同一 Thread 只出现一次；子代理折叠只影响显示。根聊天按活跃 / 待用户处理优先排序，同级保持稳定身份，避免每秒重建展开状态。
- 最近完成项以最多 10 项、最近约 10 分钟为初始显示上限，仅展示已有观测范围；活动项不按该上限淘汰。不新增历史数据库。
- 核心活动文案复用语义消息与同源中文资源，必要时构建导出展示资源；不在 Swift 手工维护工具别名或再次猜动作名称。GUI 新文案进入本地化资源，语言可用性按资源完整性声明。
- DTO 对新增字段容忍、缺失数值保留 null，未知 schema 或损坏快照进入明确不可用状态；缺少 `overview` 的旧快照可以展示兼容列表，总速度显示未知。
- 沿用当前快照过期与断连语义，文件读取失败不会保留一个看似实时的旧总速。保留最后可信静态用量与可恢复历史结果，但不继续活动计时。

## 5. 管理状态、退出与恢复

### 5.1 接入与清理分开记录

接入意图、实际配置、采集状态、清理进度分别维护；不要用一个布尔值代表全部状态。管理操作串行并持有用户安装锁，记录版本与操作代次，避免双击、多个 App 副本或配置 / 恢复并发覆盖备份。

| 状态 | 含义与可执行动作 |
| --- | --- |
| 首次未配置 | 没有历史接入与恢复记录，且环境未指向旧 Monitor；预检通过后执行一次自动配置，失败时明确报错并允许重试。发现旧入口但缺备份时进入诊断状态，不按全新安装覆盖。 |
| 已配置 | 接入意图为开启；实际仍可处于待重开 Codex、未连接、已连接或观测缺口。 |
| 已配置但退出采集 | 配置保留，GUI 与 collector 停止；已有 bridge 仅保留必要通信，重开后恢复观察并标记缺口。 |
| 已恢复、待清理 | 后续启动配置已恢复，仍有旧 Desktop / bridge / app-server 或未完成文件清理；可安全重试，不重新配置。 |
| 已恢复 | 正常恢复完成，保留少量 GUI 偏好与已恢复标记；重开保持未接入，主动配置开启新一轮基线。 |
| 准备卸载 | 已选择清理本机数据并退出；等待依赖退出并完成清理后移除自身数据与登录注册，再退出。 |
| 操作失败 / 部分完成 | 保留原配置和逐项完成记录；显示失败项与可重试动作，不把部分成功显示为全部完成。 |

配置 / 恢复记录保存原值是否存在、准确字符串值、当前代次安装值与资源归属。新接入前先验证真实 `launchctl` 对未设置 / 空字符串的可区分读取方式；不能只用 mock 返回码证明精确备份。旧备份无法证明原值时保留原件并报告边界，不以当前已改过的值补造原始状态。

原始备份在第一项环境变更前可靠落盘。每一步配置失败都按实际完成情况回滚；回滚失败保留恢复依据。恢复仅修改仍属于本代次安装值的变量，用户后来改过的值保留并记录处理结果。重复配置、升级和重装只更新本代次安装记录，不覆盖尚未完成恢复的原基线。

### 5.2 无 Helper 的启动回退

外部轻量脚本使用系统 shell 和已安全引用的参数，不在回退分支解析依赖 Python 的配置。通过独立的启用标记与固定入口判断是否调用 Monitor；缺失标记按未启用处理。

- App / 必要入口可用且接入已启用：调用当前 bridge。
- App、Python 或必要入口缺失，或接入未启用：保留 argv 与 stdio，`exec` 原版 CLI，不额外设置 Monitor TRACE。
- 原版 CLI 必须是已校验且非包装器自身的入口；更新后失效时明确诊断，不递归、不循环重试。
- 只在启动前选择路径，不把已开始通信后的任意失败都转换成重启 / 重放，避免重复执行任务。
- App 移动或升级时只更新有效入口；无法确定位置时回退，不据路径缺失自动删除备份或恢复记录。

这项验证只保证误删后新启动路径的目标行为。已运行进程的环境、App 外残留与完整恢复仍由 App 内流程处理。

### 5.3 退出停止采集

- GUI 负责 collector 的启停，collector 不依赖旧 KeepAlive 常驻。关闭面板不停止；显式退出先撤销观察会话，再停止 collector，等待有界退出结果。
- 已有 bridge 不能结束。为旁路观察增加明确的暂停 / 恢复信号：暂停后维持 stdio 与必要 stderr 处理，停止分词、事件解析 / 缓存增长等监控工作；恢复时丢弃跨暂停的半帧并标记 gap，不把暂停区间当作连续观测。
- 接入启用与观察会话分开。App 已安装但 GUI 暂停时仍保留可再接入的桥接能力；新 bridge 按会话状态进入安静观察模式，不要求用户仅为再次打开面板重启 Codex。
- GUI 会话用进程身份 / 有界心跳验证，GUI 崩溃后由现有核心自行停止采集或暂停旁路，不新增监护进程，也不结束 Codex。旧桥接未加载这一能力时显示待更新状态，不能声称全部生效。
- 已运行 CLI 的 TRACE 环境不能随 GUI 退出而立即撤销，可能仍有日志生成与过滤开销；“停止采集”不宣称整个 Codex 的 TRACE 成本归零。保持既有不向 Desktop 落盘全文观察 TRACE 的边界。

### 5.4 恢复与清理

恢复开始即阻止旧接入入口重新应用配置，停止采集；先逐项恢复并验证环境，再进入安全清理。只恢复环境成功时可显示“配置已恢复”，全部清理另有状态。

- 活动任务结束不足以证明可删除。已继承旧入口的 Desktop 仍可能创建后端，须同时核对相应 Desktop、bridge 与 app-server 的依赖，PID 核对启动身份，不能仅按进程名或裸 PID 删除文件。
- 无法排除依赖时保守保留文件，并显示等待原因；GUI 打开时周期检查，提前退出则将待清理项与可选彻底清理意图可靠持久化，下次继续。
- 默认完成恢复后保留 GUI 偏好与已恢复标记；GUI 登录偏好与 Codex 接入启动脚本分开，即使登录时打开已恢复 App，也不自动接入。
- 用户选择“清理本机数据并退出，用于卸载”时，先完成配置恢复、关闭自身登录注册和确认无依赖，再删除自身数据。保留记录直到各步骤完成；最后清除已恢复标记并退出，App 包由用户删除。
- 若中途失败，不继续删除唯一恢复记录。全部清理成功后再次打开按首次启动处理，不保留后台清理进程。

## 6. 分步实施与完成条件

### P0：只读本机 App 与构建链路

1. 建立 `macos/` 与本地构建 / 运行脚本，设置最低 macOS 26、菜单栏 App 属性和固定工作 bundle 标识。
2. 明确本机 Python 与源码定位，产物与运行状态放入忽略目录；构建不安装接入、不修改旧备份或 LaunchAgent。
3. 用开发只读模式显示一份固定快照，再读取当前快照；旧契约没有总速时显示 `—`，不临时相加 Thread 数值。
4. 验证原生菜单栏、面板打开 / 关闭、数字刷新、中文和系统材质；记录本机实际系统与工具链版本。
5. 用独立测试 bundle 标识验证登录启动方案并撤销测试注册，再固定工程与注册方式；本阶段不打开日常自动接入。

完成条件：本地 `.app` 可从 Finder 打开并只读展示数据；原日常 collector / Desktop 未被重启，接入配置未变。建立 A1 的构建与展示基础，不宣称 A5–A12 完成。

### P1：管理状态、结构化命令与隔离备份

1. 实现固定数据目录、安装锁、接入意图、观察会话与待清理状态，区分正常恢复和彻底清理。
2. 建立 `app` 命令组与 JSON 结果；Swift 命令客户端通过参数数组异步调用，不用拼接 shell 命令。
3. 拆分当前 `setup / uninstall` 的备份、写入、服务控制、恢复与清理，做到逐步持久化、幂等与失败可重试。
4. 在独立 HOME / runtime、模拟 launchctl 和原 CLI 中验证；真实环境读取的空值边界使用任务专用测试键验证，不修改日常四个接入变量。
5. 为旧备份、重复配置、恢复中断、用户后改值、损坏备份和清理失败补行为测试。

完成条件：状态与管理命令在隔离环境可走通 A5 / A7 / A9–A12 的核心路径；没有通过测试顺手改动日常接入。

### P2：总速度与 GUI 快照契约

1. 在核心建立独立流汇总与覆盖质量，复用既有源选择、逻辑 Thread 选择和镜像语义。
2. 固定 `overview`、父子关系、数据版本、空值和连接 / 过期约定；旧 CLI 看板保持兼容。
3. 验证多个流引用同一活动、父子镜像、多后端、缺少身份、未知流、仅工具执行、已完成流和历史结果等边界。
4. 给 Swift 提供不含正文的契约样本；验证旧快照、缺失 overview、损坏 JSON、有限数值与过期状态。
5. 新核心模块纳入实际依赖进程的 `source_identity()`，GUI 保存本机构建身份；后续运行分别核对 bridge、collector 与 GUI，不能只比对源码文件。

完成条件：A2 / A3 的核心与客户端契约测试通过；总速度与已观测小计有明确区别，不由 GUI 临时猜算。

### P3：菜单栏与紧凑面板

1. 接入 overview，完成 `0 / 有效总速 / 部分观测 / 未连接 / 过期` 等菜单栏状态。
2. 实现聊天列表、项目标注、父子展开、工具详情和最近完成上限，保留两个计数与两种速度的可读性。
3. 接入同源活动文案与中文 GUI 资源；选择与展开即时响应，1Hz 刷新不重置用户状态。
4. 用代表性样本检查长标题、多聊天、长项目名、未知指标、浅 / 深色、减少透明度与面板滚动；检查后台解析不会卡住菜单栏。

完成条件：A1 / A4 的只读界面完成，A2 / A3 在 GUI 中正确呈现；尚不将展示成功当作管理流程已通过。

### P4：脚本回退、观察启停与登录启动

1. 生成 App 外的安全启动脚本，配置 / 登录入口与包装器入口都做存在性和启用判断。
2. 在假 App、假 CLI 和独立 runtime 中做真实子进程验证：App / Python / 标记缺失、路径含空格、参数、stdio、信号和退出码。
3. 实现观察会话暂停 / 恢复与缺口处理；验证 collector 停止时原 CLI 工作能继续，GUI 再开不补造暂停期速度。
4. 接入已验证的 GUI 登录启动方式。关闭开关或退出 GUI 不触发 collector 的 KeepAlive 重启。
5. 验证 GUI 正常退出、崩溃、重复启动、collector 异常，以及原 CLI 自身不可用时的清楚结果。

完成条件：A6 / A8 的隔离进程路径通过；回退不是仅测试脚本文本，暂停不是结束 bridge。

### P5：首次配置、旧安装迁移与恢复 UI

1. 接入首次启动自动配置、已恢复保持未接入、主动配置，以及“恢复配置”对话中的可选清理并退出。
2. 检测当前旧安装并导入原备份 / 所有权记录；先保证恢复依据，再停用旧接入型 LaunchAgent。保留当前安装代码中的路由值，不能因 GUI 重启旧的强制路由方案。
3. 默认沿用旧 runtime 承接仍活跃的 bridge，或保留兼容入口直到旧进程退出；不在旧进程使用期间移动或清空运行目录。
4. 旧桥接能力不足时明确显示需要正常重开 Codex，不强制关闭任务。仅 GUI / collector 改动不能被当作旧 bridge 已加载新版本。
5. 在隔离状态走完整 UI 流程与迁移演练，每步失败保留可恢复结果；日常安装的实际迁移放到 P6 完成后的 P7。
6. 登录时仅对已启用状态检查 / 应用接入；若 Codex 已抢先启动且未继承环境，显示需要正常重开，不承诺任意启动顺序都能即时观察。

完成条件：A5 / A9 / A10 / A11 在隔离环境贯通 GUI 与管理服务；迁移演练保留真正接入前的基线，不把旧 Monitor 当成原版配置。

### P6：运行中恢复、安全清理与退出

1. 实现环境恢复成功、等待依赖退出、清理失败和全部完成的独立展示。
2. 建立已知 Desktop 与桥接依赖核对，验证无活跃任务但 Desktop 仍运行时不会提前删除入口。
3. 实现退出后下次继续、重复恢复、清理时失败 / 重开，以及待清理时再次配置的防并发处理。
4. 默认恢复保留状态；可选清理完成后注销登录、清除自身数据并退出。验证下一次确实是首次启动，正常恢复重开则仍未接入。
5. 清理尾声停止 GUI 定时读写与退出保存，确认 collector 已完成最后写入，再删除最终记录；避免退出回调或迟到任务重新创建已清理目录。

完成条件：A7 / A12 通过真实进程与 GUI 检查，不需要 Helper，不以删除 App 包代替恢复验收。

1. 按第 7 节运行受影响测试，复用既有相关记录；不重复全部协议盘点或无关实验。
2. P0–P6 关键路径通过后，检查当前本机原配置 / 备份并执行日常安装迁移，再做一组最小真实路径：多个已接入聊天 / 子代理生成、工具活动、菜单栏汇总、关闭面板、退出 / 重开、恢复 / 再配置。

4. 误删实验优先使用可恢复的本地 App 副本和隔离接入，验证不依赖 App 内 Python 的回退，再验证重装保留原备份。

完成条件：需求内本机路径完成且剩余边界透明。若仅完成隔离验收、日常进程尚未加载新桥接，保持该限制，不宣称全部完成。

## 8. 交付边界与参考

实施交付应包含本地构建 / 运行入口、原生源码、最小核心扩展、相关测试、真实加载与验收结果，以及更新后的使用 / 恢复说明。实施记录见 [实施结果](implementation-results.md)；源码提交状态以 Git 记录为准。

后续自包含发行需另行验证 Python 冻结、词表离线完整性、包体、启动、签名公证、GitHub Release、其他机器与系统版本兼容；不能把当前开发环境运行当作这些能力的证据。

第 3 节的原生承载与登录启动基线参照 Apple 官方接口，具体行为仍以 P0 本机构建与系统验证为准。现有协议、指标与观察边界沿用本仓库已有记录，不为 GUI 扩大或重做 Codex 逆向调查。
