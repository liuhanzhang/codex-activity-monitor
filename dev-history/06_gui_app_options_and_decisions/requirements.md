## 2. 菜单栏与展开面板

### 2.1 菜单栏

- 合计当前独立生成流；覆盖后台 Thread 与独立子代理生成，同一流不因多后端观察或父子镜像重复相加。
- 展开、折叠与列表筛选不改变总速度的统计范围。
- 正常连接且确认没有生成时显示“图标 + `0 t/s`”；未连接或不可用时显示“图标 + `—`”，原因在面板说明。
- 部分观测与完整观测必须区分，不能把未知流当作零再宣称完整总速度；部分覆盖显示 `—`，面板单列已观测小计。
- 沿用约 2 秒速度窗口和 1Hz 展示刷新作为实现起点，内部事件仍实时接收；速度显示一位小数与 `t/s`，确认无生成显示 `0 t/s`。

### 2.2 聊天列表与详情

采用紧凑列表，主聊天平铺、标注所属项目，正在工作和等待用户处理的优先。子代理归在父聊天下，可展开；工具活动详情按需展开。

| 主列表信息 | 约定 |
| --- | --- |
| 聊天 / 项目、当前活动、耗时 | 延续现有动作语义和持续时间规则，避免直接显示协议事件名。 |
| 本回合 Output / Reasoning | 两个服务端计数；Reasoning 是 Output 子集，不再次相加。 |
| 实时生成速度 | 来自已接收内容的本地分词与窗口估算，不等于完整隐藏推理吞吐。 |
| 最近推理均速 | 延续现有事后观测窗口估算与最近有效结果保留规则，不宣称纯模型推理速度。 |

保留有限最近完成项；不增加完整历史浏览、全天曲线或长期统计。当前采用最近 10 分钟最多 10 项；活动项不受此上限淘汰。数据边界沿用 [用量需求](../05_token_usage_and_reasoning_speed/requirements.md) 和 [当前实现结果](../05_token_usage_and_reasoning_speed/implementation-results.md)，新 GUI 不自行改变指标口径。

不做 Codex 聊天跳转，不复制 Codex 的审批、用户输入操作或通知。首版中文，保留多语言能力，英文后续补齐；不提供尚未完整翻译的语言选项。

## 3. App 行为与配置管理

| 编号 | 操作 / 情况 | 已确认行为 |
| --- | --- | --- |
| R6 | 首次全新启动 | 自动发现并配置 Codex 接入；接入结果与需要重开 Codex 的状态可见，不为接入强制结束任务。 |
| R7 | 点击“配置” | 启用或修复接入，检查配置与运行状态；重复操作不能覆盖尚未恢复的原始备份。 |
| R8 | 点击“恢复配置” | 撤销仍由 Monitor 管理的接入配置、停止采集；用户可保留 App 再配置，也可手动删除。保护用户后来的配置修改。 |
| R9 | 关闭面板 | 仅关闭展开内容，菜单栏和采集继续。 |
| R10 | 退出 Monitor | 关闭界面、停止采集，保留接入配置与维持现有 Codex 通信所需的桥接。退出期间的观测缺口不能冒充连续观测。 |
| R11 | 登录启动 | 提供可关闭的开关，首次设置默认开启。不得因采集器自动重启而使“退出停止采集”失效。 |
| R12 | 正常卸载 | 在恢复时选择“清理本机数据并退出，用于卸载”，完成安全清理后，由用户手动将 App 移到废纸篓；首版不提供 App 自卸载。 |
| R13 | 未恢复就删除 App | 不增加常驻卸载 Helper，不承诺自动完整恢复或立即清理；采用外部启动脚本回退原版 CLI，并支持重新下载 App 后恢复。 |
| R14 | 恢复后重新打开 App | 保持未接入，只有主动点击“配置”才再次接入，不再次自动配置。 |
| R15 | Codex 运行期间恢复 | 先恢复后续启动配置，保留仍被使用的文件，显示“等待 Codex 退出后完成清理”；不强制结束 Codex。提前退出 Monitor 时持久化待清理状态，下次打开继续。 |
| R16 | 恢复与彻底清理的区别 | 默认恢复保留少量 App 设置与已恢复状态；可选“清理本机数据并退出，用于卸载”。安全清理完成后退出，再次打开按首次全新启动处理。 |

“恢复配置”是恢复本轮接入前的原值 / 未设置状态，并保留用户后来修改的值。它不是写回统一出厂默认值。旧 Desktop 已继承的环境不会因为外部配置恢复而立即改变。

### 3.1 备份与重装恢复

- 原配置备份、接入所有权记录与轻量启动脚本放在 App 包外的固定用户目录，不随 App 包删除而一并丢失。
- 重复配置、更新或重新下载必须识别原备份，不把仍处于 Monitor 接入状态的配置另存为“安装前配置”。缺失或损坏的备份必须明确报告，不能宣称已恢复原状态。
- 重新下载后可用“恢复配置”处理旧接入；可以重新生成运行文件，但不能先覆盖或删除恢复依据。
- 新一轮接入在上一轮恢复完成后重新记录基线；未完成恢复 / 清理时不得错误覆盖旧记录。状态记录与清理顺序见实施计划，正式恢复后再配置已取得新的准确基线。
- 只清理 Monitor 自身资源；保留 Codex 登录、聊天、数据库和用户配置。旧 Desktop / bridge / app-server 仍依赖的文件不得提前删除。

### 3.2 无常驻 Helper 的误删兜底

“不加 Helper”指不增加删除监听、恢复或自卸载用的常驻进程；现有 bridge / collector 仍是核心组件。

1. 在首次配置、登录或其他实际应用接入的入口检查 App 可用性与启用状态。App 不存在时不再写入 Monitor 接入配置；旧登录脚本不能在后台反复覆盖用户的恢复操作，已恢复后再次打开保持未接入。
2. 在 Codex 实际调用的包装脚本中再次检查。App / 所需入口缺失或接入未启用时，直接启动原版 CLI，保留必要参数与 stdio 行为，不额外开启 Monitor TRACE。
3. 脚本的回退分支只依赖系统可用工具，不依赖已删除 App 内的 Python 或模块。原版 CLI 不可用时清楚报错，避免递归调用包装器。
4. 这是下一次脚本执行时的启动兜底，不是持续删除检测；不把“原 CLI 可启动”等同于全部配置已恢复或残留已清理。

仅“不再写入配置”无法撤销当前登录会话和已运行 Desktop 持有的旧配置，因此两个检查入口都需要。新旧 shell 入口已实现并通过隔离子进程回退验证；日常安装的误删循环未执行。

## 4. 已确认的恢复交互与实施设计

| 事项 | 已确认行为 / 技术设计范围 |
| --- | --- |
| 恢复后重新打开 App | 已确认保持未接入，直到主动点击“配置”。默认恢复保留必要偏好和该状态。 |
| Codex 运行期间恢复 | 已确认延后清理；GUI 显示等待状态，不提前删除依赖。提前退出后下次继续；没有后台卸载 Helper。 |
| 清理本机数据后退出 | 已确认作为恢复流程的可选项；在依赖安全退出、配置恢复成功后删除自身本机数据与启动注册并退出，App 包由用户手动删除。 |
| 外观与技术细节 | 面板尺寸、最近记录上限、部分覆盖标记、原生 API、目录与定位等由实施计划给出起点，通过最小验证调整，不再作为用户需求待定项。 |

签名、公证、自动更新及 GitHub Release 发布流程不作为当前本机阶段的前置问题；后续进入发行阶段再确定。
