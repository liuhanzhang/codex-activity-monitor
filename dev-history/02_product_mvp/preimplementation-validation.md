## 2. E1：正常 Desktop 启动路径的采集入口

### 要回答的问题

保持原版 CLI、模型模式和认证路径，能否从 Desktop 正常创建的后端同时取得完整生命周期与上游内容增量？若使用启动入口包装器，它是否会影响 Code Mode host、辅助 CLI 调用或 Desktop 退出？

### 方法

1. 复用已有启动入口、环境传递与 CLI 路径结论，核对已知 CLI 路径并执行一次正常启动 / 初始化回归。小更新不触发全量重新验证。
2. 在隔离 Desktop 中复制正常 stdio 启动路径，不直接沿用旧实验预启动 WebSocket 后端作为此实验的通过证据。
3. 执行有限长度正文生成、长 exec 参数生成、Reasoning 和一个短工具调用，逐项记录事件覆盖和可见时间。
4. 先验证原生日志是否具有完整载荷和身份字段；只看到方法名不算覆盖。
5. 若有缺口，编写最小转发原型，使用当前原版 CLI 原样传递启动参数与通信。分别验证 app-server 和非 app-server CLI 调用；不得形成包装器递归。
6. 对照隔离 Desktop 的正常完成结果，检查有无额外错误提示、缺失工具、输出截断或协议异常。

### 通过条件与分支

| 结果 | 下一步 |
| --- | --- |
| 原有入口可取得完整生命周期、上游增量及关联信息 | 使用日志 / 现有事件入口适配器，无需增加转发层 |
| 生命周期不完整但 hooks 可覆盖缺口 | 在隔离配置中验证真实回调，再决定是否采用 hooks |
| 默认 stdio 无完整旁路事件入口 | 验证透明转发器：复制协议与必要诊断事件 |
| 所有入口均缺少上游参数增量 | 阶段 A 未通过；保留明确缺口，继续定位接收层，不用 sessions 完成记录代替实时增量 |

每个接入候选都需要经过 E2 与 E4。接入路线通过后再准备日常 Desktop 配置与恢复步骤。

## 3. E2：多聊天交错时的身份关联

### 要回答的问题

增量能否在到达时就归到对应聊天？推理项、外层 exec 参数与内层工具执行之间，哪些 ID 可直接映射，哪些只存在父子关系？

### 方法

1. 在同一个隔离 Desktop / 实际候选后端中并行运行两条聊天，分别使用可区分的测试标记；测试标记只用于验收，不成为产品归属算法。
2. 两条聊天都包含正文、工具参数和工具结果，并争取出现明确的增量交错。未实际交错的运行不能验证并发关联。
3. 记录后端、连接或日志 span、thread、turn、response、item、call 的映射依据；检查重试、预热与一个 turn 内多个模型响应。
4. 核对实时归属与最终完成项 / 会话记录；逐项比对增量拼接和累计量。
5. 用离线重放验证重复事件、缺少 item 开始、未知身份和乱序。跨来源镜像事件只能选择一个计数来源，不重复累计。

### 通过条件

- 测试中所有可归属的内容流均在其完成前建立映射，不依赖事后完成文件补齐。
- 两条聊天没有串流；每个内容项的完整增量与最终对应文本一致。
- 预热、重试或无法关联的事件被隔离，不凭“最近活跃聊天”或时间接近强行归属。
- 外层工具参数生成与内层执行分别建模；有多个活动时可以同时保留。

若只能在完成后建立映射，则当前候选入口不满足实时看板，必须补充带关联上下文的入口。

## 4. E3：Tokenizer、分块边界与计算开销

### 要回答的问题

实际使用模型有没有可确认的公开编码？本地重新分词的计数与接收窗口速度是否稳定？长工具参数与多个并行流是否让采集变慢？

### 方法

1. 在项目独立虚拟环境中固定 tiktoken 版本，按实际模型核对官方编码映射及其来源。不把旧 Cookbook 中的 Codex 名称当作当前 Desktop 模型的编码说明。
2. 使用旧实验完整参数、正文与摘要，以及中文、代码、emoji 等短样本。完整文本的 tokenization 作为本地计数基线。
3. 同一文本分别使用原始分块、单字符分块和不同随机分块重放。最终计数必须与完整文本基线一致。
4. 构造末尾分词发生合并或修正的情况，观察窗口计数差值；保留修正信息，不把负差值截零后计入累计总量。
5. 测量 10 KB、100 KB、1 MB 内容流，以及 1 / 4 / 8 条并行流在 250 ms 刷新周期下的计数耗时、采集延迟与峰值内存。

### 通过条件与实现选择

- 分块方式不影响最终累计计数。
- 当前模型编码有明确匹配依据，或者界面明确标注所选编码与估算性质。
- 正文、参数与命令输出不混计，多个内容项不混拼。
- 计数任务在目标刷新周期内完成，事件队列不持续增长；超过预算则降低计数刷新频率或使用后台计数，再评估边界安全的增量算法。

可先用固定周期重算累计文本建立正确基线。窗口速度按两个计数采样与实际时间差计算；尾部修正使短窗口差值为负时，速度暂时显示不可用并保留修正记录，后续采样恢复。不能从这种修正倒推负生成速度，也不能据此篡改总量。

即使编码匹配，这个指标仍定义为“接收文本的本地 token 计数速度”。与实际服务端生成的 token 边界及内部全部输出用量的差异应保留。

如果实际模型编码无法确认，仍可继续第一版，但 token/s 必须标注估算并记录编码。不能静默退回无标注的固定字符比例。

## 5. E4：最小运行可靠性与开销

此实验在接入日常 Desktop 前完成最小检查；全面长期运行验收仍属于后续阶段 D。

### 方法

- 对同一候选入口，分别验证正常完成、取消、工具失败、等待审批和后台命令持续运行。
- 停止看板 / 聚合器，验证 Desktop 任务仍可运行；使旁路队列积压，验证不会阻塞协议转发。
- 若采用转发器，验证 stdin EOF、stdout / stderr 关闭、退出码、SIGTERM 传递和正常 Desktop 退出；解析异常不应污染协议 stdout。
- 若采用 hooks，验证执行开销、缺少成对结束回调及同步 / 异步回调行为。
- 若采用日志读取，验证部分末行、轮转、截断与恢复。启动时的历史积压应单独重放，不显示成刚刚高速生成。
- 对启用与未启用采集的同类有限任务记录首增量延迟、工具调度、CPU、内存、日志量。模型耗时有波动，少量对照仅作为异常开销排查，不能证明零开销。

### 通过条件

- 监控异常或看板退出后，Codex 的通信与工具运行仍正常。
- 没有因监控引入的持续队列增长、死锁、孤儿运行进程或协议错误。
- 终止与断流后能关闭或标记旧活动，不永久显示运行中。
- 接入配置能够恢复，恢复后 Desktop 按原路径正常运行。
- 日志与内存消耗有测量数据；高频原始 trace 有有限记录边界，不无界落盘。

若转发器自身无法继续正常转发，应使失败明确可见并提供原路径恢复；不能宣称它的崩溃对承载中的任务没有影响。上述“监控异常”主要指旁路消费者与解析故障，关键转发进程的故障风险须单独记录。

## 6. 稳定的实现骨架

通过实验的入口作为可替换适配器。核心职责按以下顺序拆分，暂不预建空目录：

| 模块 | 输入 / 输出与职责 |
| --- | --- |
| 来源适配器 | 原始协议 / 日志 / hook → 来源事件；版本适配与增量读取 |
| 身份关联器 | 来源事件 → 具有明确归属的事件，或未关联事件集合 |
| 活动状态 | 已关联事件 → 每条聊天的活动集合、阶段与终止状态 |
| 文本与计数 | 独立内容流 → 暂存文本、本地累计 token、采样和修正信息 |
| 指标聚合 | 状态与计数采样 → 阶段时间、接收窗口速度、最近进展 |
| 终端展示 | 聚合快照 → 实时表格；不负责猜测身份或解析来源 |

实现时采用包内模块与清晰的数据结构，不将全部功能堆入实验脚本。命令入口支持实时运行与离线重放，以相同聚合逻辑处理两者。

### 最小归一化事件字段

```text
schema_version
source_kind / source_version / source_instance
source_timestamp_utc（可空） / observed_timestamp_utc / observed_monotonic_ns
backend_id / thread_id / turn_id（未关联时允许空）
response_id / item_id / call_id / content_part（按实际入口提供）
event_kind / sequence_number（可空） / mapping_basis
payload（delta、生命周期、工具摘要或终止结果）
observation_quality
```

来源时间和读取时间分别保存。直接接收的增量可以按观察端单调时钟计算窗口；尾读日志需验证刷新延迟，并保留日志接收层时间。离线重放按来源时间计算，不能把读取文件的速度当作模型接收速度。

运行模式只将 tokenizer 所需文本暂存在内存中；输出项结束后保留计数与摘要指标。原始正文、参数与诊断 trace 的持久化仅用于有限实验，不作为默认长期存储。身份未关联、观察时间未知与估算编码等标记必须传递到界面。
