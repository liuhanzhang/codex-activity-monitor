## 1. 用户问题与产品目标

用户经常并行多个 Codex Desktop 聊天。提交任务之后，工具信息默认折叠，流式生成期间也缺少持续可见的反馈，因此难以判断每条聊天当前在做什么、最近是否有进展，以及生成速度如何。

第一版提供所有可观测本机聊天的实时总览，让用户在一个地方看到阶段、持续时间、正文与工具参数的接收速度。成功标准是用户能在真实并行任务中据此了解运行情况。

| 生成速度 | 正文、工具参数使用本地 tokenizer 计算接收 token/s |

阶段与指标决定已经确认。终端表格、刷新周期和 tokenizer 计算策略是实施选择，应通过真实效果验证。

- 正式桌面 UI、菜单栏、置顶窗口或视觉设计。
- 远程主机采集、跨设备汇总。
- 自行发送通知或处理审批。
- 隐藏 reasoning 内容、连续隐藏 reasoning token 速度。
- 完成百分比、剩余时间预测。

## 3. 实时看板

每条本机聊天显示以下信息：

| 字段 | 含义 |
| --- | --- |
| 聊天名称 / ID | 能与 Codex Desktop 对应；缺少名称时显示可区分的 ID |
| 项目 / 工作目录 | 方便区分同名聊天，字段缺失时允许为空 |
| 当前阶段 / 活动 | 等待响应、Reasoning、正文生成、工具参数生成、工具执行等 |
| 阶段持续时间 | 从明确的阶段开始事件计算的经过时间 |
| 接收 token/s | 正文、工具参数分别计算；并行流可分别展示 |
| 本段累计 token | 当前输出项在所选 tokenizer 编码下的累计计数 |
| Reasoning summary 增长 | 累计 Unicode 码点数；有明确段落边界时可增加段数 |
| 最近进展 | 距离最后一次收到内容增量或确认阶段变化的时间 |
| 采集状态 | 正常、观测不完整、断开或无法关联 |

默认突出运行中和等待用户处理的聊天，完成的聊天保留最近结果以供核对，不发送通知。空闲历史聊天可以隐藏，筛选规则后续按使用效果调整。

初始刷新目标为每秒 2–4 次，速度采用最近 2 秒窗口。此参数用于第一版试用，不构成已经验证的性能承诺。

以下是示例，不是实测数据：

```text
聊天        当前活动                 持续时间  接收 token/s     本段累计      最近进展
登录功能    生成工具参数 · exec       12s       约 150（估算）   1,820 token   0.2s 前
架构分析    Reasoning · 摘要 126 字符 18s       —                —             4.1s 前
修复测试    执行工具 · pytest         32s       —                —             0.7s 前
```

## 4. 阶段与活动语义

| 状态 | 证据与展示方式 |
| --- | --- |
| 等待响应 | turn 已开始，但没有更明确的阶段证据 |
| Reasoning | 明确 reasoning 项目开始事件；持续时间更新，摘要到达时累计数量 |
| 正文生成 | 收到正文 delta，显示该项速度与累计量 |
| 工具参数生成 | 收到工具输入 delta；区分外层 exec 输入与内层工具执行 |
| 工具准备 / 执行 | 使用完整生命周期、状态字段或执行事件，不把待审批误报为已执行 |
| 等待审批 / 回答 | 明确请求事件；只显示状态，不生成通知或代为响应 |
| 完成 / 中断 / 失败 | 使用权威 turn / item 终止事件 |
| 状态未知 / 观测中断 | 缺少关键事件、连接中断或身份无法关联 |

一条聊天可能同时有多个工具或生成活动。内部维护活动集合，表格显示主要活动和并行活动数量，详情保留其他活动；不能用一个全局阶段不断覆盖所有活动。

具有明确进程身份的后台命令可以超过聊天回合的生命周期。回合完成或下一回合开始不直接结束该命令，使用它自身的权威完成事件；主行注明回合已经完成。观测中断时将活动标为未知，不继续声称已知运行。

Reasoning 持续时间表示开始事件以来经过的时间。无摘要增量时只更新时间，不声称隐藏 token 持续生成。明确结束时固定时长；关键结束事件缺失时标记观测不完整，不无限保持“正在推理”。只有摘要事件而缺少开始事件时，注明开始时刻未知。

“最近进展”仅使用有内容或有运行意义的事件。连接保活和重复状态快照不能持续刷新它。无事件不能据此判定卡死。

## 5. Token 指标契约

### 5.1 计数对象

- 正文、工具参数、reasoning summary 分别聚合，命令输出不计入模型生成 token/s。
- 每个 response / item / 内容部分独立累计，避免不同内容和身份被拼接为同一文本。
- summary 首版以字符增长展示；如增加 token 计数，使用同样的编码标注。
- 本地 token 计数表示收到文本在所选编码下的分词结果，不宣称恢复服务端原始生成 token ID 或全部输出用量。

### 5.2 Tokenizer

使用 OpenAI 维护的 tiktoken 验证本地计数。记录实际模型、tokenizer 版本、编码名称和匹配依据。无法确认模型编码时明确标为估算；不凭模型名称前缀静默采用未经验证的编码。本轮 tiktoken 0.14.0 未列出当前 gpt-6-* 模型映射，第一版明确采用 o200k_base 作为估算编码。

编码确认后，文本在该编码下的计数可以精确复现，但本地文本计数与服务端总输出用量仍是不同指标。后者可能包含隐藏 reasoning、格式或结构 token。

### 5.3 增量与速度

不能把每个 delta 单独分词后直接相加。传输分块可能切开 token，追加文本也可能改变末尾分词。第一版优先使用按固定刷新周期重算累计文本的方式建立正确基线；出现性能问题后再验证边界安全的增量算法。

保存各内容流的计数采样，窗口速度根据累计计数变化与实际经过时间计算。分词边界重算可能产生短暂计数修正，需要区分修正与新增接收量，不能把负差值简单截为零后累加。长流与任意分块重放应具有一致的最终计数。

窗口计数差值因尾部修正而为负时，暂时显示速度不可用并保存修正信息，后续采样恢复；累计量保持真实重新计数的值。正式采用前按 E3 实验检查短窗口表现和计算开销。

显示的是观察端的接收速度，网络缓冲会导致短时波动。没有新内容时窗口速度自然下降；生成阶段结束后固定本段累计量和接收均速，不把工具执行中的无输出解释成生成速度为零。

完成后的服务端 usage 用作独立用量信息或验证证据。不能直接拿总 output_tokens 与可见文本计数要求相等，也不能根据最终 reasoning 用量倒推实时思考速度。

参考：[官方 tiktoken 说明](https://developers.openai.com/api/docs/guides/embeddings#how-can-i-tell-how-many-tokens-a-string-has-before-i-embed-it)、[官方用量计数边界](https://developers.openai.com/api/docs/guides/token-counting)。

## 6. 采集与接入约束

### 实验已经支持的方向

- 隔离 Desktop 后端的正文和长工具参数增量可观测。
- 工具参数 delta 拼接后与完成项和持久化记录一致。
- Reasoning 开始 / 结束、摘要增量可见，连续隐藏 reasoning token 计数不可见。
- app-server 生命周期与上游增量需要结合，才能区分参数生成与实际工具执行。

### 产品接入仍需验证

- Desktop 正常启动的实际后端是否能稳定提供完整事件与上游增量。
- 多条并行聊天的 response、turn、item 与工具身份能否明确关联。
- 日志、hooks 或转发入口的覆盖、开销、退出行为和版本兼容性。

采集必须对准 Desktop 正在使用的后端。独立启动一个共享 CODEX_HOME 的 app-server，不代表它能观察 Desktop 的活跃任务。

本轮选择透明 stdio 转发器：Desktop 启动同一个原版 CLI，转发协议，同时旁路采集。独立 Desktop 的包装器启动回归和自有 stdio 后端的真实并行回合已通过。当前环境变量与日志格式属于版本适配点；小更新复用已有结论并做有限回归。

首次配置与重启已获用户接受，但在重启前应准备完整接入与恢复步骤，并确认没有需要保留的活跃任务。不能把当前监控能力尚未就绪的重启当作验证成功。

## 7. 实施顺序

### 阶段 A：真实接入与身份验证

按验证方案执行 E1（接入入口）、E2（并发身份关联）；E3（tokenizer）可同时准备。

1. 记录安装版本与启动路径，检查实际 Desktop 后端的日志、事件入口和关联字段。
2. 利用已有隔离实验验证采集器，保持原有模型、tool mode、prompt 与认证路径。
3. 在两条并行聊天中验证正文、长工具参数、Reasoning 与工具执行的分界和身份关联。
4. 选择能够覆盖需求的接入路线；不足时实现并验证转发器。
5. 准备首次接入和恢复步骤，再验证实际日常 Desktop 路径。

第 5 步之前先完成 E4 的最小可靠性检查。完整可靠性与长期性能验收继续放在阶段 D。

产出：接入方案、字段映射、两条并行聊天的证据与明确缺口。仅离线重放或隔离后端成功，不能通过日常 Desktop 接入验收。

### 阶段 B：采集器、聚合器与 tokenizer

首版验证程序优先沿用现有 Python 脚本生态，避免为正式 UI 提前引入应用框架。

1. 归一化事件，保留 host / backend、thread、turn、response、item 与来源身份。
2. 实现去重、序号检查、断流检测、无法关联事件隔离和并行活动状态。
3. 按实际模型验证 tokenizer 编码，计算文本累计 token 和窗口接收速度。
4. 用已有精简证据与诊断 trace 重放验证，再接入实时数据。

产出：可实时运行的本地采集与聚合程序，以及可复现的计数验证。

### 阶段 C：终端实时看板

1. 显示活跃本机聊天、主要阶段、并行活动、阶段时间、summary 增长与速度。
2. 支持展开活动详情，显示指标来源及估算 / 观测不完整标记。
3. 在真实并行工作中试用，记录哪些信息有用、哪些仍不能解释等待。

产出：用户可以直接运行并观察真实数据的最小产品。之后根据试用反馈设计正式 UI。

### 阶段 D：运行可靠性

验证失败、取消、审批、重连、日志轮转、Desktop / CLI 退出，以及采集器异常。测量响应与工具调度延迟、CPU、内存和日志写入量，再决定持续运行配置。

高频 trace 在实验中产生过较大的日志；解析后丢弃文本并不能消除上游写入开销。正式路径应限制诊断记录时长与容量，或验证只提取必要事件的采集入口。

产出：试用操作说明、实际性能数据、版本适配边界和可恢复的接入方式。

## 8. 验收标准

| 场景 | 必须观察到的结果 |
| --- | --- |
| 两条聊天同时生成 | 状态、内容计数与速度准确归属，各聊天之间没有串流 |
| 长工具参数 | 参数尚未生成完时已有累计量与速度；执行开始后阶段正确转换 |
| 长正文 | 完成前持续显示累计量与窗口速度 |
| Reasoning 静默 / 摘要 | 持续时间更新；摘要到达后累计增长；无虚构隐藏 token 速度 |
| 工具并行 / 审批 | 活动可以重叠；待审批不误报为已经执行 |
| Token 分块变化 | 同一完整文本采用不同传输分块时最终计数一致 |
| 重复 / 未关联事件 | 不重复累计；不把无法关联的数据强行归给当前聊天 |
| 失败 / 取消 / 断连 | 不永久显示旧活动运行中；呈现终止状态或观测缺口 |
| 日常 Desktop 使用 | 完成首次接入后按正常方式使用，无需为每条聊天重新配置 |
| 旁路采集、解析或看板退出 / 异常 | 不阻塞 Codex 的通信和工具执行；关键转发层的故障风险与恢复路径单独验证 |
