# 发布类型解耦、Pages 上线与真实更新验收

日期：2026-10-28。用户已明确要求开始实施并授权使用 gh 操作 GitHub；该授权覆盖本轮提交／推送、Pages 配置与发布、准备的新版本 Release。原先等待远程操作授权的边界在本轮解除，不再重复确认。

## 规则

- `version-suffix` 只组成显示版本和 tag，不推断发布类型。
- `release-prerelease` 是明确的布尔发布配置，决定新构建的默认频道并与 GitHub Release 的 Pre-release 标记核对。它可以与版本后缀任意组合。
- 已安装 App 的默认频道固定于构建；GitHub 上修改发布分类会改变更新清单的归属，不会远程改写客户端偏好。
- 已发布条目的分类和发布时间从 GitHub 校验／同步，不再要求版本后缀与分类相同。稳定频道只包含 `prerelease=false`，预发布频道包含全部已公开且有可用安装包的条目。
- 新客户端使用 `appcast-prerelease.xml`；旧 `appcast-alpha.xml` 作为内容相同的兼容地址保留。Preview 仍禁用检查。

## 发布顺序

1. 保留当前用户日常构建 2，备份初始 index／diff。实现解耦和回归测试，准备隔离的 HTTPS 验收模式。
2. 将当前功能发布为 `0.1.0-alpha.3`、构建 3，明确 `release-prerelease=true`。保留原有 Alpha 的发布状态，这不是由名字推断分类。
3. 检查本轮 allowlist、相关测试、构建和签名，通过后提交推送。启用 Pages 的 Actions 部署，先上线现有已发布条目的真实清单。
4. 构建并验收新安装包，创建指向已验证提交的 Release，上传 ZIP／SHA256SUMS，发布为 Pre-release。
5. 将新发行加入清单，使用 GitHub 返回的发布分类／时间同步并验证后，提交清单并部署。
6. 公网 HTTPS 验收：独立构建 2 测试客户端发现 3；下载的构建 3 不提示更新；新的独立偏好验证自动检查而非手动按钮触发。测试标识和数据目录与日常实例隔离，不改系统时间、不向生产清单写入合成高版本。
7. 补充实际提交、Release、Pages、CI 与验收证据。用户日常 App 保留构建 2 供观察，不自动安装／不重启 Codex。

首次 Sparkle 之前的原始公开安装包不含检查功能，不能自行发现这次升级。已更新的本机源码构建 2 包含 Sparkle，可以作为旧客户端；公开下载安装包的完整验证使用隔离副本。

## 完成标准

代码中没有根据版本字符串／后缀选择频道的逻辑；相反分类组合的单元测试通过。GitHub 标记、ZIP 内默认频道、公开 appcast 和实际 SDK 检查结果一致；旧更新源 URL 仍可读。把实际公网请求、提示／已最新、构建号和 SHA-256 分开记录，既有本地测试不替代本轮公网验收。
