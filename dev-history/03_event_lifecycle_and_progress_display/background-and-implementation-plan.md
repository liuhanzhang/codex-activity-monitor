# Monitor 改进：问题背景、查证与实现计划

日期：2026-10-12。状态：87/87 实现前对照与实施后消费边界复核完成，P0 / P1 及有依据的 P2 已实施；81 项回归、6 份捕获回放、核心隔离实测及日常运行切换已验证；未触发场景与原生窗口截图边界单独保留。详见 [实现与验证结果](implementation-results.md)。以下保留原定计划与验收条件。

本次改进的目标是让用户一眼知道 Codex 当前在做什么、工作是否仍在继续，并看到实时生成速度。下一步先逐项复核全部 87 种通知的现有实现、查证执行信号与采集边界，修复状态问题，再落实简洁的用户界面。

本文是下一步工作的入口。逐项事件取舍见 [事件消费与展示决策](event-display-decisions.md)；当前代码与协议事实见 [App-server 事件盘点](app-server-event-inventory.md)；工具参数、执行与审批的证据见 [工具生命周期与审批状态](tool-lifecycle-and-approvals.md)。已有名称和命令预览改动见 [工具活动名称与命令显示](tool-activity-display.md)。

## 1. 问题背景

初版 monitor 已接入日常 Codex Desktop，能够观察部分回合、模型文本、工具参数和命令活动。使用中暴露出三个相互关联的问题。

首先，界面的状态与用户理解的工作不对应。“工具准备 / 执行未确认 · exec”无法让用户分辨工具尚未执行，还是已在执行但 monitor 缺少证据；`exec → exec_command` 又把 Code Mode 的外层调用和实际命令工具直接暴露出来。用户真正需要的是“准备命令 · rg …”或“运行命令 · pytest …”。生成参数时也应尽早显示已识别的工具名和命令摘要。

其次，消费链有缺口。CLI 有工具开始、结束和审批相关消息，但 monitor 的字段过滤、身份关联和状态处理并不完整。某些消息只是透传，没有影响状态；有些必要字段已被删掉。因此，不能把“收到一个事件名称”等同于已经支持该活动。

最后，默认展示的信息偏技术化。摘要字数、输出字数、token 累计量和内部工具层次增加阅读成本；审批、用户输入等操作提示则已经由 Desktop 承担。需要让 monitor 更像简洁的进度总览，并把实时流式生成速度作为主要新增价值。

产品方向按本轮沟通确定：展示用户可理解的真实工作动作；内部消费必要事件以保证准确；不重复 Desktop 的审批、问答、登录或验证操作。

本轮补充：自动审核过程可以展示为“自动审核中”；上下文压缩过程明确展示为“压缩上下文”。这两类是系统正在进行的工作，与要求用户操作的客户端审批分开处理。

- 已盘点 87 种服务端通知、11 种服务端请求、19 种活动类型、10 种已接入模型流事件及 84 种 core 事件路径。它们处于不同层次，不是 211 种独立客户端消息。

### 2.2 已定位的问题

| 问题 | 已确认的原因 / 事实 | 影响与修复方向 |
| --- | --- | --- |
| 外层调用长期停在“执行未确认” | 参数完成与内部工具运行来自不同事件流、使用不同身份；当前没有可靠父子关联 | 将参数准备与执行分开；用户界面优先展示有证据的内部实际工作。 |
| 命令开始语义不统一 | 审批前可以发出 `item/started`；拒绝后也能收到完成项 | 开始项不一律等于进程已启动，批准也不能替代启动证据。 |
| 协作活动缺失 | 协议为 `collabAgentToolCall`，当前类型集合写成 `collabToolCall`；复数接收聊天身份未保留 | 修正类型及关联字段，分别处理派发调用与子任务状态。 |
| 模型配置未正确更新 | 实际 payload 为 `threadSettings.model`，当前过滤和消费使用平层字段 | 保留正确的最小嵌套配置，更新模型与分词选择。 |
| 请求已结束，仍可能显示等待 | 正常 `serverRequest/resolved` 带 `threadId`，当前清理分支只覆盖另一种形状 | 按请求身份统一清理阻塞；未观察到决定时保持未知。 |
| 自动审核消息没有语义消费 | 审核身份、目标、结果等被过滤，引擎没有对应分支 | 补齐独立审核生命周期，展示自动审核中；不重复人工审批操作。 |
| 恢复和等待阶段不准确 | 错误、认证恢复等丢弃；部分进度消息仅透传 | 区分重试、终止、仍在处理与观测缺失，避免残留生成状态。 |
| 外层完成使用推断规则 | 新 reasoning / 正文可以关闭旧外层活动 | 不能将该规则当作 cell 或后台进程结束证明。 |

上述字段 / 类型 / 清理问题已有经过真实过滤器和状态引擎的合成诊断；命令启动和审批拒绝也有既有捕获证据。合成诊断证明处理缺口，schema 证明消息形状，二者都不能替代当前 Desktop 的端到端运行验证。

## 3. 本次产品与展示范围

默认列表保留聊天 / 项目、当前活动、活动耗时和一列“生成速度”；普通详情只补充用户可读的并行活动、简短结果、计划步骤和子任务状态。

| 情况 | 默认呈现 |
| --- | --- |
| 模型生成文本或可见思考摘要 | 生成回答 / 思考中；有可观测生成流才显示速度。 |
| 模型生成命令 / 工具参数 | 准备命令 · `rg --fi…` / 准备操作 · 可读工具名。 |
| 确认实际执行 | 运行命令、修改文件、搜索网页、调用工具等动作及必要摘要。 |
| 所有前台工作确实等待用户 / 客户端 | 已暂停；不显示问题、审批理由、选项、链接、按钮或提醒。 |
| 自动审核进行中 | 自动审核中；并行时在活动详情保留审核进度，不显示风险分数、长理由或人工操作入口。 |
| 上下文压缩进行中 | 压缩上下文；结束后切换到下一实际动作，只收到完成事件时不反造进行中阶段。 |
| 已知程序等待或恢复 | 等待中、正在重试、连接服务等简短状态。 |
| 只知当前回合有效，执行证据不足 | 处理中；不能写成运行命令。 |
| 回合或任务结束，或观测断开 | 显示实际结果或连接中断；观测中断不等于任务失败。 |

不进入默认界面的内容包括外层 Code Mode 名称、协议 / 进程 ID、token 累计量、摘要字 / 段数、输出字数、原始日志和用量限额。正文、完整计划、diff、工具结果与操作提示继续由 Desktop 展示。

“稳步推进”通过真实动作变化、可观测文本速度和有效的活动耗时表达。没有新增内容时不伪造百分比、剩余时间或隐藏推理速度；心跳不算工作进展。

逐项决策中，87 种通知建议必需消费 30 种、条件消费 18 种、忽略 39 种；11 种请求建议必需内部消费 6 种、条件消费 3 种、忽略 2 种。19 种 item 识别最小类型与边界，不为每个类型新增展示。core 通过实际协议投影或已有模型流消费，避免重复订阅、重复计数。

## 5. 实现计划

### A0：逐项复核全部 87 种通知的现有处理方式

已有盘点包含 87 行当前支持情况，展示决策也已逐项分类；这提供了初始判断，但“已展示 / 仅透传 / 丢弃”标签不足以证明现有实现符合新的产品规则。本阶段必须逐项阅读已有处理路径并作出明确的改进结论，不能只修几个已发现的缺口。

对每个通知按“协议 payload → 桥接 / 过滤 → 引擎 → 指标 / 展示 → 缓存重放”的适用路径核对，记录以下内容；不适用的环节说明原因：

| 逐项记录 | 要回答的问题 |
| --- | --- |
| 事件定义与作用范围 | payload 有哪些必要字段？是聊天、回合、活动还是后端级？是否实验或兼容接口？ |
| 当前实现与源码位置 | 哪个分支处理？字段是否保留？是明确语义消费还是只登记身份 / 透传？无处理也要明确记录。 |
| 目标消费与展示 | 是否需要消费？是否展示？即使不展示，是否影响阻塞、结束、模型、速度或恢复？ |
| 处理结论 | 保留现有、修复现有、补充处理或维持忽略；条件消费明确启用条件。 |
| 具体改进方式 | 需要调整哪些字段、关联、状态、去重、计速、展示或重连规则？现有实现满足需求时明确无需改动。 |
| 阶段与验证依据 | 分配到 P0 / P1 / P2 或无需改动；列出源码 / schema、回放 / 测试依据与真实触发状态。 |
| 未确认点与兜底 | 依赖哪项查证？没有对应事件时如何保持准确？未实测不得标为真实运行已验证。 |

处理结论的含义：

- **保留现有**：当前语义与新需求一致；可能只沿用对应回归验证。
- **修复现有**：已有消费，但字段、生命周期、并行优先级、速度或呈现需要调整。
- **补充处理**：需要消费但目前丢弃或仅透传；新增最小语义及必要展示。
- **维持忽略**：与本轮进度无关，保持不消费；若当前存在无效透传，注明是否收紧过滤。

同一通知可拆出不同处理任务。例如 `item/started` / `item/completed` 必须进一步按 19 种 item 类型检查；“已展示命令”不能作为这些通用通知已完整符合需求的结论。11 种 server request 及客户端回复仍是配套检查对象，不能因它们不属于 87 种通知而遗漏等待状态闭环。

交付方式：在 [逐项决策表](event-display-decisions.md) 及其 [JSON 清单](event-display-decisions.json) 中补齐上述实现复核记录；当前表里的展示取舍继续作为输入，必要时依据查证结果更新。

完成条件：与协议基线比较方法集合，**87/87 都有现有处理证据、处理结论、改进方式 / 无需改动理由、实施阶段和验证依据**，无缺项或重复；条件与未实测项明确标注。87/87 静态复核不等于全部事件都已真实触发，也不要求为忽略事件新增处理或展示。

按用户确认，先完成全部 87/87 对照并形成差异清单，再开始代码修改。运行版本交付前，涉及状态或速度的改进项完成相应回归；长尾真实触发的限制另行报告。

### P0：修复必要消费与状态准确性

1. 在过滤层明确保留最小身份、作用范围、状态和摘要字段：修正协作类型 / 复数接收身份、嵌套模型配置、请求及审核字段；保留错误重试标记、thread activeFlags 和必要结束信息。参数、正文和审核理由继续有界处理，避免完整保存。
2. 将模型生成活动、客户端待决请求、自动审核、真实工具活动和后台运行分别记录。关联键包含后端身份及可用的 thread / turn / item / request / review 身份，不能只按目标工具 ID 存一条审核。
3. 按回复与 resolved 清理对应请求。结束等待与决定是否可知分开处理；空目标审核和后端级请求不能套到所有聊天。请求结束也不能关闭仍在运行的工具。
4. 消费 thread / turn 边界、错误、重试、认证恢复以及模型流的完成 / 失败 / 不完整终止。单条 response 失败先结束其生成流，整个任务结果仍按权威回合与恢复事实决定；idle 不直接等于成功。
5. 调整主状态：有真实工作优先展示动作；所有前台工作确实被阻塞才暂停。自动审核具有独立进行中 / 结束状态；没有其他实际工作时可成为主状态，并行时也保留可见活动。命令参数完成或审核通过不作为实际执行证据。
6. 补齐重连的最小快照、关闭标记和重复事件处理；观测缺失时停止速度并使过期状态失效。后台进程按独立生命周期维护。

### P1：统一日常动作与生成速度

1. 建立集中且可复用的用户动作映射。名称或命令可识别时即时补齐，准备与运行使用不同文案；外层 Code Mode 留在内部上下文。不能解析动态命令时等待运行时摘要，不执行生成代码。
2. 识别全部 item 的最小类型与边界；增加文件、网页 / 图片、计划、子任务、压缩上下文和 sleep 的紧凑呈现。自动审核展示“自动审核中”，结束后按真实结果清理并切换活动。未知工具使用已观测短名，未知语义不猜测。工具结果、用户输入和注入项不展示成新的生成阶段。
3. 按结构化 plan snapshot 显示步骤状态；重新规划后更新分母，不造任务百分比。区分代理派发 / 等待调用与子任务真正运行或结束；单次完成项只补结束事实。
4. 将现有正文 / 参数等速率归并为一列聊天生成速度，包含去重后的回答、计划、参数和可见摘要。原始文本流仍按身份分别计量，父聊天的子任务镜像不重复累计。
5. 约 2 秒接收窗口内的有效生成流可以显示速率；未知 encoding 标记估算。没有可观测生成流时显示 `—`；结束内容只校正计数，不倒填实时速度。命令输出、进度消息和服务端 usage 不计入。
6. 移除默认技术字段，保留具体动作、耗时和必要并行上下文。合并短暂等待，保持状态连续；失败、终止和断线立即呈现。1 秒 / 3 秒的初始合并阈值通过回放调整。
