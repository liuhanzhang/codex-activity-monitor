# 全面改名实施步骤

日期：2026-10-26。状态：P0–P6 已完成，最终证据与边界见[实施结果](implementation-results.md)。下文保留实施顺序与验收条件。

按“核对旧安装 → 暂停并恢复旧接入 → 改名与验证 → 仓库和目录更名 → 新安装切换 → 清理与复核”推进。运行数据清理服务于改名，不先开展无关的历史资料整理。

## P0：固定基线与清理清单

1. 记录 HEAD、工作区 diff、Git remote 和 worktree 列表。实施时重新检查；此前有 worktree 的情况不代表现在仍有，2026-10-26 最新盘点仅有主工作区。
2. 只读列出旧 App、Preview、独立包、数据根目录、runtime、归属标记、安装记录及登录 / LaunchAgent 状态。区分真实会话和实验自建 profile，不读取或导出聊天正文。
3. 按范围表形成明确的可删除路径清单。不能对 `experiments/` 整目录删除，也不能仅凭 `.local` 名称就认定其中所有文件可以立即删除。
4. 检查目标 GitHub 名称和本地目录是否冲突，确认仓库更名权限与可用工具。工具不可用时寻找已有授权渠道；不能只改 `origin` 就宣称远程仓库已改名。

通过条件：源码和开发资料保留边界清楚，后续不会依赖被提前删除的环境、launcher 或原配置备份。

## P1：暂停旧监控，恢复旧接入

1. 正常退出旧 GUI，防止它在后台重新配置接入或续租。只暂停 Monitor，不主动强杀正在进行任务的 Codex。
2. 使用旧版本现有恢复流程，按当前值与本安装值比对后恢复原 GUI-session 环境，保留用户后续修改。必要的原环境备份仅暂存于权限受限的本机位置，不提交到 Git。
3. 停止旧 collector，检查生命周期锁确实释放；核对旧可选 LaunchAgent、GUI 登录注册与旧 App 路径。旧标签清理必须在代码改为新标签之前完成，或使用显式的旧标签清理分支。
4. 核对仍运行的 Codex / bridge 是否依赖旧源码、Python、runtime 或 launcher。恢复接入变量不代表既有进程已经换了环境。
5. 对尚被依赖的旧入口保留最小可用文件。需要用户重启 Codex 时，在安全交接点明确提示；用户重启前，不删除仍在使用的依赖，不强制结束当前聊天。

通过条件：旧接入已恢复或有明确待完成项，collector 已停，必要的恢复依据仍在。若仍有驻留依赖，后续可在独立构建目录推进新版本，最终删除必须等依赖释放。

## P2：产品、代码与构建全面改名

1. 移动 Python 源码包和 CLI 脚本；修改 `pyproject.toml` 的发行包名、命令入口和模块路径。
2. 同步修改产品、测试及实验源码的 import、动态 patch 路径、子进程 `-m` 参数、源码存在性校验和打包 hidden imports；不遗留指向旧模块的运行入口。
3. 修改 Swift Package 名、App / Preview 名称、`CFBundleName`、`CFBundleDisplayName`、ZIP 名以及启动、打包、检查和验收脚本中的对应路径。沿用已经正确的主 App / 后端 / Preview Bundle ID。
4. 修改窗口、错误、菜单、无障碍和终端里的固定产品名；中英文保持一致。活动名称和来源正文不作为产品名替换。
5. 修改默认数据目录、项目自有环境变量、标记内容、合成 profile 类型、构建 / benchmark 前缀和可选 CLI 服务标签。读写两端与测试期望一起更新。
6. 核对新版的旧安装清理入口：不能因改了默认目录或服务标签而找不到尚未处理的旧安装。仅保留必要的显式清理逻辑，不默默导入旧监控历史。
7. 修改 README、贡献说明、打包说明及实际存在的 CI / 开发入口；修复指向当前源码的历史导航链接，保留原始证据字符串。
8. 通过 `bin/export-localizations` 重新生成共享词库和本地化测试示例；检查 Swift Package 改名后资源 bundle 仍能加载。

通过条件：新名称的源码、CLI、GUI 和打包脚本一致；保留旧名称的位置均有历史或一次性清理用途。

## P3：在隔离环境验证改名

先使用临时 runtime、合成 fixture 和 read-only Preview，不把真实日常配置作为测试 fixture。新建虚拟环境，避免旧 editable install 让旧模块“偶然还能导入”。

1. 在干净环境安装新包，检查发行元数据、`codex_activity_monitor` 导入、`python -m codex_activity_monitor.cli --help` 和新 CLI 入口。
2. 运行现有 Python 回归套件；管理流程用注入环境 / 服务验证新路径、新标记与恢复清理，不能触碰真实 `launchctl` 设置。
3. 运行本地化导出一致性检查和 Swift 测试，核对 fixture、预期标题与资源 bundle。
4. 构建只读 Preview；核对 App 名、plist 中显示名 / ID、窗口标题、错误提示及无障碍产品名。
5. 构建独立包，检查 ZIP / App 名、外层与嵌套 Bundle ID、后端导入、依赖与许可证清单；按现有隔离验收流程验证源码目录外运行。所需环境不具备时明确记录未完成，不能以普通 GUI 构建替代。
6. 定向扫描产品代码、测试、脚本、当前文档和生成资源中的旧名称。历史档案、Git 历史、明确的旧安装清理常量单独审阅，不要求这些位置零命中。

基本检查命令，以下均在最终仓库根目录执行：

```sh
.local/venv/bin/python -m unittest discover -s tests -p 'test_*.py'
.local/venv/bin/python bin/export-localizations --check
swift test --package-path macos
bin/build-gui --preview
bin/codex-activity-monitor --help
```

测试随改动验证 import、路径、品牌资源和接入边界；不为字符串替换重复增加无行为价值的测试。出现失败或实施内容变化时再补充必要验证。

## P4：更名 GitHub 仓库与本地目录

1. 将远程仓库改为 `LiuHanzhang/codex-activity-monitor`，实际检查新仓库入口；保持现有可见性、权限和提交历史。
2. 更新 `origin` 为 `git@github.com:LiuHanzhang/codex-activity-monitor.git`，验证远程可读。不自动提交 / 推送工作区改动或此前已有的 7 个未推送提交。
3. 在旧安装依赖允许后，将本地主目录改为 `/Users/bytedance/personal/codex-activity-monitor`。若实施时新增了 linked worktree，使用对应的 Git 移动 / 修复流程并检查，不直接修改 Git 内部路径记录。
4. 确认后续命令和 Codex 的项目 / 工作目录能转到新路径；不要靠保留永久旧目录软链掩盖未更新的依赖，也不直接改写 Codex 内部数据库。
5. 在最终路径重建 Python venv / editable install、Swift 缓存和 App。重新生成 `backend.json`、launcher、安装配置中所有绝对路径，不能复用移动前的构建结果作为日常安装。
6. 从最终路径再做 CLI、本地化检查及 GUI 构建冒烟验证，确认新产物未引用旧源码目录。

通过条件：远程名称、`origin`、本地根目录与实际构建使用的路径一致；Git 历史和原有未推送提交完整保留。

## P5：新安装与日常切换

1. 使用最终目录下的 `Codex Activity Monitor.app` 配置全新数据根目录和接入。保留原版 Codex CLI 的正确路径，不把 Monitor 的 launcher 当作原版 CLI。
2. 检查接入环境的实际值、安装记录、GUI 登录启动状态、collector 所有权和默认数据路径；新安装不能因旧记录残留而被误判为已配置。
3. 明确提示用户手动重启 Codex，让新启动的后端继承新接入。已授权暂停监控不等于授权强制结束用户正在运行的任务。
4. 重启后确认 bridge 来自新版、新 runtime 的 collector 可连接、GUI 能看到真实活动；用一个自然回合检查活动、时间线、结束状态和计数。不能只凭 App 打开或 plist 正确就认定切换完成。
5. 核对旧源码、Python、runtime 和旧 App 不再有驻留依赖，再完成旧注册与入口清理。若需要等待用户重启，记录“待重启 / 待清理”，保留最小过渡依赖。

通过条件：日常运行实际使用新名称和新路径，旧安装不再被调用，接入原值的恢复能力仍然正确。

## P6：清空旧生成物，记录实际结果

1. 按 P0 的明确清单删除旧监控数据库、快照、日志、实验运行数据、隔离测试 profile、旧 App / ZIP、旧缓存和已不再被使用的环境。
2. 保留 Git 跟踪的开发资料、实验脚本、合成 fixture、图标、许可证及 Codex 自己的数据。对路径符号链接和所有权有疑问时停止该路径的删除，不扩大到父目录。
3. 检查旧数据目录、旧服务注册、旧 GUI 登录项、旧源码入口及旧发行包残留；确认没有重复 collector 或两套 App 互相覆盖接入。
4. 记录清理路径和实际释放空间，不将 P0 的目录总大小当作已释放空间。新构建产生的缓存和新运行数据属于本轮有效安装，不能为了“零数据”再删除正在使用的文件。
5. 新建 `implementation-results.md`，列出实际改动、验证命令与结果、仓库 / 安装最终路径、数据清理结果，以及仍需用户重启或进一步验收的事项。更新本章状态和开发历史索引。

## 中断与回退

- 改名中的代码、远程 URL 和本地目录可按记录回退；不使用覆盖用户改动的 `git reset --hard`，不改写 Git 历史。
- 旧监控数据已获准清空，删除后不能承诺恢复。原环境备份必须保留到旧接入恢复完成；临时备份用完即清理，不成为长期历史迁移。
- 若源码检查已通过但日常切换失败，保留可审查改动和准确状态，先恢复可用的原版 Codex 入口；不能把失败的新安装留在接入变量里后报告完成。
- 改名验收与长期稳定性、Remote、Developer ID 签名、公证和干净机器验收分别记录，不借本轮改名更新这些未完成结论。
