## 实现结构

| 模块 | 职责 |
| --- | --- |
| `bridge.py` | 原 CLI 参数传递、协议字节转发、必要诊断消费、有限旁路队列、信号传递 |
| `events.py` | 仅传递进度相关协议与上游事件，过滤用户输入和隐藏 reasoning 内容 |
| `collector.py` | 0600 Unix socket、进程互斥、周期聚合、指标快照、重启后的历史指标恢复 |
| `engine.py` | 后端作用域身份映射、未关联隔离、重复/乱序处理、活动集合、断连与终止 |
| `metrics.py` | 按累计文本重新分词、2 秒接收窗口、计数修正、共享重算预算、结束后释放文本 |
| `display.py` | Rich 实时表格、聊天筛选、活动详情、来源/估算/质量标记 |
| `integration.py` / `cli.py` | 安装、登录启动、显式 Desktop 启动、卸载恢复、离线重放 |

采集器与看板不承载 Codex 协议通信；旁路消费者异常会丢弃有限观测数据并标记缺口。包装器本身仍是关键传输进程，它的崩溃可能影响承载任务。

实时并发样本的正文峰值约 132.5 token/s、参数约 165 token/s，均为本地估算接收速度，只说明产品确实在结束前给出反馈。首个长参数样本没有捕获内层 commandExecution，不能据此判定它完成了 shell 执行；真实命令执行由后续后台恢复样本提供证据。最终的语义与恢复改动另外由核心/运行测试及真实捕获重放覆盖。

命令的 `inProgress` 项可能早于审批请求，因此产品不依靠 100 ms 等待等启发式判断已经执行。审批/回答有明确状态；明确的 unified execution 来源与进程 ID 表示已有进程启动证据，立即显示执行工具；其他命令仍以输出或完成事件确认。缺少开始事件时详情注明开始未知；终止事件缺失或重连不会制造历史速度。

真实后台样本表明 unified execution 命令可以在生成它的回合完成后继续运行。聚合器保留具有明确进程身份的此类活动，主行标注“回合已完成”，直到自己的完成事件到达；下一回合开始也不会提前清除它。观测断连时仍停止将其显示为已知运行状态。

重连缓存保留有限的终止元数据，避免漏收结束后重新播放开始事件造成永久活动；完整完成文本不进入缓存。恢复后的同项最终指标可从先前快照保留。旧 socket 的结束不会断开已接管的连接。身份冲突、流计数失效、过期快照与事件缺口均停止相应速度展示；重复生命周期不刷新“最近进展”。

Desktop 生成聊天标题时会创建单独的 ephemeral 任务，它与用户聊天有不同的完整 ID。默认终端视图依赖明确的 `ephemeral` 元数据隐藏临时任务，诊断 JSON 仍保留；不会按短 ID、无名称或最近活跃时间猜测归属。接收通道只将 Received message / SSE event 交给解析器，无关帧诊断直接消费；一个读取批次中的多条事件合为一个有界队列包。发送端使用非阻塞 socket，保留已写入的帧偏移，只由独立观察线程等待可写；不因 100 ms 暂停重连。队列仍受 128 包 / 8 MiB 限制，停止时排空最多 750 ms。实际故障分类、发送等待次数与采集器关闭连接的原因进入指标诊断。

第三轮真实任务期间记录到 43 次等待 socket 可写，没有转为断连或观测丢弃；长正文最终与会话文本计数一致，所有新任务 quality 均为空。Reasoning 阶段约 9.30 秒；本轮没有增量摘要，故不宣称验证了日常摘要频率。短参数与两段很短正文的完整计数已收到，但生成结束前没有正速度快照。

第二轮采样在断连前出现约 707 ms 快照间隔，与短暂停顿机制相符；当时没有发送错误类型记录，因此不能把模拟的 TimeoutError 当作现场捕获的错误。350 ms 暂停回归明确复现了原代码的超时和后续离线丢弃。普通输入请求及 userMessage 生命周期中的用户正文均在进入 IPC 前过滤。

## 性能与持久化

这是有限排查数据，不能证明真实模型延迟完全不受影响。

- 空闲采集器的一次采样 RSS 14,528 KiB，进程生命周期平均 CPU 0.7%；空白快照 179 字节，collector.log 0 字节。这不是分词工作期峰值内存。
- 实时样本计数开销最大约 145.23 ms，包含首次载入编码。计数工作在单独线程，合计重算成本会降低长文本/多流的计数频率；原分词规模对照继续复用 [实现前数据](/Users/bytedance/personal/codex_progress_monitor/analysis/product-preflight/tokenizer.json)。
- 本地热态 100 次约 1 KB 回显：原程序往返中位 0.012 ms，包装器 0.030 ms；P95 为 0.022 / 0.043 ms。样本没有模型调用或真实网络日志。
- 2.31 MB 连续回显的整体进程耗时中位增加约 496.54 ms，包装器 RSS 约 23 MB；这包含 Python 启动与结束时有限旁路排空，不能将它直接解释为每次工具/首 token 的额外延迟。冷启动测量存在明显波动。
- 停滞观察线程压力样本：2,000 次 offer，队列保持 4 包 / 262,144 字节，丢弃 1,996 包，offer 总耗时约 3.29 ms。原始协议转发不等待解析或 socket 消费。
- 实时指标快照按 250 ms 原子替换，文件本身保持有界，仍有持续写入成本；长期自然使用的 CPU、I/O 与更多并行流数据尚待记录。

默认运行不额外存储原始 trace。为了取得上游增量而启用的 SSE / WebSocket TRACE、DEBUG 在包装器内消费，普通诊断继续转交 Desktop。Codex 本来就会持久化的会话/日志不属于监控器新增存储。

有限传输回归还验证了 stderr 消费端关闭后仍继续排空子进程诊断，协议可以完成；超过 10 MiB 的未结束诊断行整行丢弃并记缺口，后续普通诊断继续转交，不转交被截断行的尾部。这些测试使用自有模拟 CLI，不等同于真实模型性能测量。
