机制解释及边界
公开源码 core/src/tools/handlers/apply_patch.rs:78 的专用参数增量消费者，
会解析直接 apply_patch 的输入流并生成 PatchApplyUpdated，缓冲间隔为 500ms。
它受 ApplyPatchStreamingEvents 开关控制。
本次用当前安装的 CLI、全新的临时 CODEX_HOME 执行离线 features list，确认
apply_patch_streaming_events 为 under development，默认 false。
code_mode_host 默认 true；code_mode、code_mode_only 默认 false。
features list 的默认值不等于当前 Desktop app-server 的最终有效配置。
core/src/tools/mod.rs:64 表明模型元数据 tool_mode 优先于上述模式开关。
core/src/session/turn.rs:2148 只为模型层工具名注册专用增量消费者；
该源码只有 apply_patch 实现了这个消费者。
外层 exec 生成 JavaScript 时，内层 apply_patch 的字符串不是该消费者的输入。
这能解释实验现象，但没有抓取当前安装二进制的原始上游响应来逐段证明。

补充：exec 的来源与调用方式
exec 是 Codex 内置 Code Mode 的 freeform 工具，不是实验脚本自定义的工具。
code-mode-protocol/src/lib.rs:45 定义工具名 exec。
core/src/tools/code_mode/execute_spec.rs:23 注册 ToolSpec::Freeform，
输入语法是原始 JavaScript，允许首行 // @exec: 控制返回等待时间与输出预算。
code-mode-protocol/src/description.rs:12 描述工具功能：在新的 V8 isolate 中
执行 async module，经 tools.* 编排实际工具，经 text/image 返回结果。
当前安装的 CLI 二进制包含相同的 JavaScript 编排、原始 JS 输入、
无 Node/直接文件系统/直接网络/console 等描述字符串，和原始 JS 输入错误文案。
core/src/tools/code_mode/execute_handler.rs:31 解析输入并提交运行时执行。
core/src/tools/spec_plan.rs:430 根据 CodeModeOnly 隐藏可嵌套工具的直接模型入口；
:452 把嵌套工具规格传给 exec，并注册 exec/wait 执行器。
core/src/tools/mod.rs:64 优先采用模型的 tool_mode 元数据。
因此该模式下，要求“使用 apply_patch”的 prompt 仍可通过 tools.apply_patch 满足，
并不意味着模型具有直接调用 apply_patch 的顶层入口。
实验脚本中的 developerInstructions 未要求使用 exec 或 JavaScript。
实验启动器 :178 确实设置 code_mode_host=true；core/src/thread_manager.rs:346
表明该选项选择进程级 host 或 in-process session provider，不决定 tool_mode。
上述 Rust 源码仍是较旧公开快照，不等于安装二进制的完整逐行源码。
OpenAI Docs 的 Programmatic Tool Calling 文档也介绍了用 JavaScript 编排工具的
通用设计；API 的托管实现与这里 Codex 的本地运行时不能当作同一接口。
https://developers.openai.com/api/docs/guides/tools-programmatic-tool-calling
